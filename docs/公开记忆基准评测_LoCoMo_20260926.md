# MemWeave 公开记忆基准评测：LoCoMo

日期：2026-09-26

## 1. 为什么选 LoCoMo

LoCoMo 是公开的长期对话记忆基准，包含 10 段长对话、272 个会话、1,986 个带标注问答。每道题给出答案所在的对话轮次 `D<n>:<turn>`，可以转换为答案所在的 `session_<n>`，因此适合先评测 MemWeave 的检索层：查询是否找回了真正支持答案的会话。

它不能单独证明自动入库、知识治理或下游回答质量，所以本项目把它定位为“公开召回基准”，与自然表达准入集、LFHV 误杀恢复实验分开报告。

数据来源：[snap-research/locomo](https://github.com/snap-research/locomo)。数据许可证为 `CC BY-NC 4.0`，只用于本地非商业评测，不随 MemWeave 商业发布包分发。

## 2. 评测脚本

脚本是 `scripts/evaluate_locomo_retrieval.py`。它会：

1. 将每个 LoCoMo session 导入临时 SQLite，不写入正式 `data/knowledge.db`。也支持 `--granularity turn` 作为诊断实验。
2. 使用当前 MemWeave 的 SQLite FTS5、BM25、中文 n-gram 和仲裁链路检索。
3. 将返回的知识记录映射回原始 session，计算 `Hit@1`、`Hit@K`、平均 Recall@K、MRR 和检索延迟。
4. 单独统计无证据问题是否保持空结果。

全量复跑：

```powershell
git clone --depth 1 https://github.com/snap-research/locomo.git $env:TEMP\locomo
$env:PYTHONPATH="src"
& "C:/Program Files/Python312/python.exe" -X utf8 `
  scripts/evaluate_locomo_retrieval.py `
  --dataset "$env:TEMP\locomo\data\locomo10.json" `
  --output outputs/locomo-retrieval-run `
  --limit 5
```

输出：

- `report.json`：总指标和按题型指标
- `cases.jsonl`：逐题的证据、召回结果和诊断信息
- `by_category.csv`：便于 Excel 查看

## 4. 结果怎么解释

这轮证明了三件事：

- FTS5 + 中文 n-gram 在长对话 session 级召回上已经可用，普通题的前五候选大多包含证据。
- 多跳题是当前短板，问题通常不是“完全找不到”，而是证据分散、排序靠后，导致 Hit@1 和 MRR 下降。
- “不应该注入”仍是明显缺口。按 LoCoMo 口径，类别 5 的 446 道对抗题和类别 3 的 4 道无证据题都作为负向题，当前 450 道全部返回候选。后续需要把 abstention 规则接到召回仲裁层，并用专门的负例集扩大验证。

`limit=1/3/5/10` 的对比结果如下：

| limit | Hit@1 | Hit@K | 平均 Recall@K | P50 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 65.56% | 65.56% | 60.70% | 6.60 ms |
| 3 | 65.56% | 83.00% | 77.60% | 9.60 ms |
| 5 | 65.56% | 89.91% | 83.68% | 7.92 ms |
| 10 | 65.56% | 95.00% | 90.70% | 10.68 ms |

这说明当前主要矛盾是排序和候选覆盖，而不是基础查询速度。单纯把 `limit` 调大可以提高覆盖，但会增加注入噪声，不能作为最终方案。

## 4.1 粒度诊断：不能直接把 session 替换成单轮

脚本增加了 `--granularity turn`，用于验证主体一致性方案。按单轮导入、`limit=10` 的结果为：Recall@10 64.10%、MRR 45.07%、P50 31.36ms、P95 48.89ms，明显低于 session 粒度。

这排除了一个看似合理但效果更差的改法：单轮文本太短，多跳问题失去相邻线索，且记录数增加会放大检索成本。后续应采用混合方案：

1. 用 turn 级索引定位最小证据单元，并保留 speaker、session、时间戳。
2. 以命中的 turn 为锚点，只扩展前后有限窗口，或扩展同一 session 内的高相关 turn。
3. 对问题主体与证据 speaker 做一致性检查，避免“问 Melanie、命中 Caroline 发言”这种对抗误注入。
4. 最终上下文仍以 session/window 形式提供给 Agent，控制注入字符数和延迟。

## 4.2 本轮修复：主体与证据一致性

本轮在 Core 中加入了可选的 `subject_terms` 元数据和答案充分性门。它解决的不是“候选和问题沾不沾边”，而是进一步判断“这些候选是否已经具备回答问题的必要条件”：

- **候选相关性**：候选至少与问题共享可检索线索，适合进入证据池；这一步允许保留弱证据，避免把多跳问题的前半段过早丢掉。
- **答案充分性**：问题明确点名主体时，候选集合还必须覆盖同一主体、问题关系（谓词）和对象/时间线索；关系缺失时，即使主题词相同，也不能注入。
- **空结果是合法结果**：当候选只有主题相关性、但不足以支撑回答时，检索返回空结果，并在 `retrieval_diagnostics.omitted` 中记录 `insufficient_answer_evidence`。
- **多跳边界**：关系和对象可以由多个证据单元共同覆盖，但这些单元必须来自同一 `source_session`；不同会话的同名主体或主题不能拼成一个答案。

本轮在 Core 中加入了可选的 `subject_terms` 元数据和证据准入门：

- 结构化 Adapter 可在写入时记录证据主体，例如 `Caroline`、`Melanie` 或服务名。
- 查询从当前项目可检索记录中构造主体词表；当问题明确指向某个主体时，其他主体的候选会标记为 `subject_mismatch`。
- direct、bridge、sibling、anchor 四条路径都在最终仲裁前复核，扩展路径不能绕过主体检查。
- 没有主体元数据的旧记录保持旧行为，避免历史数据库升级后大面积漏召回。
- 证据不足会记录 `insufficient_evidence`、`generic_term_only` 或 `insufficient_answer_evidence`，保留在检索诊断中。

`subject_terms` 表示事实真正涉及的主体；`evidence_speaker` 只表示这条证据由谁说出，二者不能混用。LoCoMo 导入器目前只写入 `evidence_speaker`，不会把发言者自动伪装成事实主体。session 粒度把多个 speaker 合并在一条记录中，只能验证兼容性；要真正测“问 Melanie 不召回 Caroline”，必须使用带事实主体标注的 turn/window 记录。

本轮 session 级对照结果（`outputs/locomo-retrieval-20260926-subject-final2`）：Hit@1 65.73%、Hit@5 90.14%、MRR 75.18%、负向净空率 0.00%，P50/P95 约 20.8/23.6ms。这里的 0.00% 不能解释为答案门无效：LoCoMo 的负向题在当前导入方式下仍是 session 级文本，且没有“这道题应该拒答”的独立答案标签；session 内还可能包含大量与主题相近的内容。因此它只能说明“session 级候选检索会找到相关文本”，不能证明最终答案是否有足够证据。主体隔离和答案充分性必须在带事实主体、关系和对象标注的 turn/window 评测集上验证。

检索链路现在按以下顺序执行：候选生成 → 扩展 → 主体/证据仲裁 → 答案充分性门 → 排序与截断。答案门的诊断字段位于 `retrieval_diagnostics.stages` 的 `answerability` 阶段，记录输入、输出、淘汰数量和原因；单条淘汰记录会进入 `retrieval_diagnostics.omitted`。这样可以区分三种情况：

1. 没有找到相关候选；
2. 找到了主题相关候选，但主体、关系或对象不完整，不能回答；
3. 找到了足够证据，可以注入给 Agent。

目前的实现对没有 `subject_terms` 的旧记录保持兼容，这类记录不会被答案门强行判定为不相关。发布前应逐步为新写入的事实补齐主体、关系和对象元数据，再用结构化负例评测自动拒答率，避免“兼容旧数据”掩盖证据不足。

## 4.3 答案充分性验收集与噪声收敛

LoCoMo 只能提供长对话检索证据，不能直接标注一条候选是否足以回答问题。因此新增了一个不含外部数据的本地契约集：

- 输入：带 `subject_terms`、`source_session` 的结构化知识记录和人工标注的问题。
- 输出：回答性命中率、拒答净空率、可回答问题的额外注入记录数、P50/P95。
- 覆盖：完整证据、主题相关但缺关系、主体冲突、对象误识别、同会话多跳、跨会话多跳和无法解析的问题。

运行命令：

```powershell
$env:PYTHONPATH="src"
& "C:/Program Files/Python312/python.exe" -X utf8 `
  scripts/evaluate_answerability.py `
  --output outputs/answerability-run
```

| 指标 | 结果 |

| 可回答命中率 | 100%（6/6） |
| 拒答净空率 | 100%（3/3） |

这组结果只证明答案门在受控样本上的行为符合契约，不代表真实对话准确率。后续应把真实脱敏会话抽样成同样的标注格式，重点观察“答案命中但多注入噪声”和“多跳证据被误删”两类错误，再决定是否扩大关系词表或引入模型复核。

## 5. 和 MemWeave 三层目标的对应关系

| 目标 | LoCoMo 能验证什么 | 仍需什么 |
| --- | --- | --- |
| 真实表达下的注入判断 | 对长对话问题，候选是否包含证据 | 明确“应该不注入”的自然语言负例 |
| LFHV 恢复价值 | 不直接验证 | 继续使用受控误杀实验和真实任务配对实验 |
| 自动采纳边界 | 不验证 | 使用 `memory_decisions_natural_20260926.json` 和后续线上脱敏样本 |

因此，LoCoMo 结果不能写成“MemWeave 记忆准确率 89.30%”。准确表述是：

> 在 LoCoMo 的公开长对话证据会话检索评测中，按独立对话 scope 运行的 MemWeave Recall@5 为 89.91%、MRR 为 74.98%，本轮只测检索，不代表最终回答正确率，也不代表自动注入策略已经解决。

## 6. 后续评测顺序

1. 先补一套与 LoCoMo 同规模的无关问题、临时例外、项目排除和旧版本冲突负例，测 `abstention clean rate` 和误注入率。
2. 对 LoCoMo 的类别 1 多跳问题增加 query decomposition 或证据合并实验，比较 Recall@5、MRR 和上下文字符数。
3. 再选 LongMemEval 的小规模子集，重点测 knowledge update、temporal reasoning 和 abstention。LongMemEval 数据页面需单独确认使用条款，不能与 LoCoMo 的许可证混写。
4. 最后才做模型回答质量评测，比较 baseline、MemWeave auto、oracle 三组，报告答案正确率、误注入率、首 token 增量和总延迟。
