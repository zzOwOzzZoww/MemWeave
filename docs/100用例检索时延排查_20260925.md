# 100 用例检索时延排查

日期：2026-09-25。

## 结论

已找到用户截图对应的两份原始 `retrieval_report.json`，确认检索 P50 约 354 ms、Adapter P50 约 1250 ms 是实际保存的测量结果。两份报告的 Recall@3 与 MRR@3 都为 1，无关请求注入率为 0；这次异常主要在时延。

当前代码在相同电脑上重新执行完整 100 用例，包括 Git Bash 的 `mktemp -d` 命令，未复现该时延。当前没有修改召回算法、关闭治理或跳过审计，也没有把快速重测当作修复成功。历史慢速运行的精确根因仍未确定。

## 计时口径

`scripts/evaluate_memweave_live_100.py` 的 `prepare_case` 每个用例构造一个 `ClaudeLearningAdapter`，之后才开始计时 `adapter.recall()`。

- `retrieval_ms`：从 Adapter 内的计时点到 `KnowledgeStore.search` 返回，包含既有轮次查询；真实带 transcript 的输入还可能涉及 transcript 解析。本脚本不传 transcript。
- `adapter_ms`：整个 `adapter.recall()` 调用，包括 Agent 启用检查、检索、上下文构建、审计落库、命中统计和影子探针入口。
- Adapter 对象构造、数据准备、Python 进程启动都不计入 `adapter_ms`。
- 测试直接调用 Python Adapter；不是原生 Codex/Claude 客户端 Hook 的完整链路，不包含 Runtime HTTP 往返，也没有首 token 测量。请求 Agent 名称不同不代表启动了对应原生客户端。
- `--retrieval-only` 不调用 DeepSeek，模型速度、额度无法解释这一组数字。

Precision@3 固定以 3 为分母。这组正例每次返回一条正确知识时为 1/3，不表示有 2/3 的错误知识被注入。

完整 prepare 流程（含构造、事后读取）共 1190 次 SQLite 连接/关闭。6.392 秒分析时间中，SQLite `execute` 累计 2.297 秒、`close` 1.753 秒、`commit` 0.809 秒、连接函数自身 0.380 秒。说明当前实现确有较多数据库交互，不能把所有开销归到排序或扩展算法。

## 已确认与未确认

已确认：慢速历史报告真实存在、数据集一致、当前重测输出一致、当前主要时间落在 SQLite 相关操作、两种 shell 与两类输出目录当前均未复现慢速。

未确认：慢速运行当时的源码摘要、进程负载、存储等待、连接/提交/关闭分别耗时。报告没有保存这些证据，不能把杀毒扫描、系统负载、旧代码、磁盘故障或某个算法直接定为根因，也不能将历史 1.25 秒全部归因为初始化——构造本来就不在该测量内。

后续定位应给运行报告增加源码摘要、Python/SQLite 版本、实际输出路径、有效召回配置及可选分段计时，等待慢速重现时对照。统计参数应使用白名单，不能保存整份环境变量或凭据。

连接生命周期复用、重复 schema 初始化，以及兼顾一致性的审计事务安排是可评估的优化方向；应先证明收益，并验证并发删除、停用、轮次幂等和审计完整性。此次没有为降低分数关闭安全或治理检查。
