# MemWeave 知识准入、按需注入与 LFHV：策略调研和验证标准

日期：2026-09-26。状态：调研与建议，尚未实施或验证新策略。

本次目标是为三个已确定方向寻找可执行的方法：什么值得保存及自动采纳、什么值得在当前轮次注入、已归档内容如何恢复与淘汰。环境适配不另立开发方向，公开发布整理继续后置。

## 1. 结论先行

有可借鉴的策略，但本次查阅的资料没有提供适用于所有 Agent 的统一“可复用标准”或可信通用阈值。

最适合 MemWeave 的组合是：

1. **准入采用有证据的选择性自动化**：允许自动采纳、待审、跳过、冲突待核对等不同结果；先限制可自动处理的类型，再用标注案例校准。模型自报置信度不等于真实性概率。
2. **注入评估当前任务的增量需要**：知识有效只是前提；还要相关、有当前上下文缺少的信息，并在预算内。检索到了不代表应该注入。
3. **LFHV 采用有界淘汰历史与恢复验证**：影子命中提示可能过早归档；有效性、现有知识是否已覆盖、恢复后是否产生用途，需要另外验证。保留“未知”状态，不能把没再使用直接当成无用。

这是一套待验证的工程组合，不是对原创性、准确率或长期净收益的证明。

## 2. 调研范围与证据等级

### 2.1 方法

围绕三个问题定向查阅论文原文、作者仓库、官方概念文档及已有 Hermes 源码。不属于穷尽式系统综述，不声称覆盖截至当天所有新工作。

检索概念包括 memory admission、memory extraction/update、selective prediction、risk–coverage、retrieval relevance/usefulness、forgetting/retention、ghost cache、cache admission、temporal memory evaluation、abstention。

纳入资料需包含具体机制、可读源码或可复核评测定义。营销措辞、无法读到的实现、跨不同环境的性能宣传不能作为本项目验收标准。没有运行外部框架、付费模型或真实用户实验。

### 2.2 核验方式与限制

- 论文机制用原文核验，论文结果只代表其报告的任务和设置；不移植其百分比作为 MemWeave 效果。
- 源码只证明抓取版本存在该路径，提示词要求不证明模型总能遵守。
- GitHub main 和文档可能变化，保留抓取时间、URL、文件 SHA256 和原文快照。
- Hermes 在线工具文件请求返回 429，本次未绕过限流；改查本机已有源码，且明确标为**本地无 Git 版本元数据的快照**，不声称等于当前上游。
- LoCoMo README 首次按小写文件名请求返回 404，后核实真实名称是 `README.MD`。
- 缓存论文解决的是访问与容量问题，不承担知识正确性判断；它们只能作为治理机制的类比来源。

## 3. 现有策略及取舍

| 资料 | 核验到的机制 | 对 MemWeave 的用途 | 不应直接照搬的部分 |
| --- | --- | --- | --- |
| Hermes 本地源码 [S1] | 小容量常驻 memory/user 信息；add/replace/remove；任务经验放入按需技能；跳过临时进度、原始数据堆等 | 明确“哪些类别值得长期保留”，并控制常驻上下文预算 | 它的常驻记忆和技能路由不等于我们的共享库；不能将所有记录每轮加载 |
| Mem0 当前源码 [S2] | 当前 main 的 add 路径先查已有记忆，再调用 additive extraction，批量 embedding 和 hash 去重；提示词要求来源归属、避免回声提取 | 提炼前核对已有知识；区分新信息与复述；保留归属 | 提示词有 “When in doubt, extract”，更偏向避免漏记；不符合我们直接自动采纳的风险目标 |
| LangMem 官方文档 [S3] | 区分 semantic/episodic/procedural；区分交互中写入与后台提炼 | 重判断放后台；不同类型采用不同准入标准 | 文档明确交互中写入会增加可感知延迟；后台也有延迟可见性，不是立即记住 |
| Generative Agents [S4] | 相关性、最近访问和重要性组合检索；重要性由模型打分 | 多信号排序的基础对照 | 社交模拟中的“重要”不等于编码任务的可信或有用；原权重不是我们的最佳权重 |
| Self-RAG [S5] | Retrieve、IsRel、IsSup、IsUse 分别处理是否检索、材料相关性、回答支持度和回答用途 | 将一个模糊判断拆成多项可测判断 | 原方法涉及训练与反思 token，不是复制几个提示词就能获得同样能力；IsSup/IsUse 部分发生在生成之后 |
| CRAG [S6] | 检索评估器产生 Correct/Incorrect/Ambiguous 路由，筛选文档内容并可能扩展到网页检索 | 接受不确定性，避免相关性不足时强行注入 | 原文的 lightweight 是其设置下的比较；不意味着对 MemWeave 零成本，更不意味着要加网络搜索 |
| Selective Classification [S7] | 用拒绝判断换取较低的已接受样本错误率，观察 risk–coverage | 自动采纳率与错误率联合评估，避免全自动或全人工两个极端 | 论文的保证有模型、数据和统计假设，不能凭 LLM 分数照搬其风险保证 |
| MemoryBank [S8] | 遗忘曲线 `R = exp(-t/S)`，调用后增加强度、重置时间 | 给保留策略提供时间和频度基线 | “被调用”不等于“有用”；直接强化会放大错误召回，低频关键约束也可能被误淘汰 |
| ARC [S9] | 使用有界淘汰历史/ghost cache，依据访问变化调整近期性与频度的平衡 | LFHV 的反馈与预算管理可借鉴 | ghost history 本身不是新概念；缓存 miss 不等于知识带来的任务损失 |
| TinyLFU [S10] | 准入时比较新项与待淘汰项的近期频度；紧凑计数和老化 | 防止归档恢复时只增不减；恢复也需考虑有限容量 | 热门程度不能替代真实性；不能单凭低频删除关键知识 |
| LongMemEval [S11] | 500 个问题，覆盖提取、跨会话推理、时间推理、知识更新、拒答 | 设计更新/时间/缺失证据用例，检索与回答分开评测 | 主要是长期对话问答，不直接验证原生跨 Agent 注入或归档收益 |
| LoCoMo [S12] | 长对话与时间信息，QA/evidence 标注及对抗问题；发布集 README 为 10 段长对话 | 测远距离事实联系、改写和错误前提 | 部分对话由模型生成再人工编辑；不等于自然使用分布，也不是自动采纳真值集 |

### 3.1 一个需要纠正的常见概括

Mem0 的 `prompts.py` 确实仍包含 ADD/UPDATE/DELETE/NONE 的旧式更新提示词，但这次同时核对了 `memory/main.py`：所抓取的 add 主路径使用的是 `ADDITIVE_EXTRACTION_PROMPT`。因此本报告不将四操作描述成该版本每次 add 必经的实际流程。设计研究需要核对调用点，不能只读一个模板常量。

### 3.2 Hermes 带来的启示

本地 `tools/memory_tool.py` 将常驻记忆限制在跨任务长期适用事实，临时 TODO、进度和完成日志留给会话历史；`agent/prompt_builder.py` 还要求用事实陈述而不是伪装成高优先级命令的句式保存。

可以借鉴其分类标准，但不必把 MemWeave 改成 Hermes 的 memory/skills 架构。我们的用户级偏好与项目知识仍可存在同一存储中，关键在于范围和按需供给。

## 4. 第一层：知识准入和自动采纳

### 4.1 将“值得记住”拆为六项

| 维度 | 标注问题 | 自动化边界 |
| --- | --- | --- |
| 来源依据 | 原话或事件是否直接支持这条结论？说话者是谁？ | 用户自述可支持“用户表示/偏好”；不自动证明外部世界事实 |
| 持续用途 | 是长期偏好、项目决策、重复可用经验，还是一次性状态？ | 没有统一天数可代替判断；用户明确要求保留应单独处理 |
| 内容完整 | 主体、对象、范围是否明确？离开原句仍能理解吗？ | “那个接口用这个地址”不能直接泛化保存 |
| 新增信息 | 已有知识或当前来源中是否重复？ | 同义复述合并为候选关系，不能凭多个 Agent 复述增加独立可信度 |
| 冲突与时间 | 是否被纠正、替代？“之前”和“现在”是否不同？ | 确认的用户偏好更新与未确认的外部事实冲突不能走同一规则 |
| 内容与权限 | 是否是凭据、未经允许的共享内容、引用中的恶意指令？ | 明确排除，不能以“用户提过”为理由传播 |

不建议先把六项任意加权为一个分数。先定义硬条件和可解释结果，再用标注数据判断是否需要学习权重。

### 4.2 建议的决策结果

- `auto_accept`：证据明确、范围明确、类型在自动化白名单中、无未决冲突；仍先形成 candidate，再写入有来源的批准依据，保留治理链。
- `needs_review`：有未来价值但证据、指代或范围不够确定。
- `skip`：一次性无保留意图的信息、无新增信息、无法支持的推测；仅保留最小决策原因，不为“以后可能有用”无限保存原始聊天。
- `conflict_review`：有可能替代旧知识，但现有依据不能自动确定。
- `merge_proposal`：同义信息待合并或关联，保留独立来源与版本，避免自动把部分不同事实合并丢失。

先允许自动采纳的窄类别建议：用户明确的持续偏好、明确且无歧义的项目决策、用户明确要求保存的非敏感事实。宽泛推断与总结暂不纳入。受检查支持的经验只能保存检查实际证明的范围，不将“运行成功”升级为“根因已确认”。

### 4.3 必须把三件事分开

1. 用户说“我住在合肥”，来源支持用户自述；用户问“我是不是住在合肥”，不支持同一事实。
2. 用户说“以后默认浅色”，支持持续偏好；用户说“这次截图先用浅色”，只支持当前任务。
3. Claude 输出的知识经 Codex 再次复述，不是第二份独立证据。需保留来源链，识别来自注入上下文的回声。

候选一天到期表示审核窗口结束，不表示事实被证伪。即使现有状态共用 quarantined，也需保留 `review_expired` 与 `explicit_rejection` 的原因区别。

## 5. 第二层：本轮是否注入

### 5.1 判断顺序

先核对知识状态、授权与范围、有效性，再判断当前问题相关性、是否提供增量信息和是否值得占用上下文。两层都是门禁：可信度高不能弥补不相关，相关性高也不能弥补错误或过期。

“是否需要历史记忆”可以做轻量提示信号，但第一版不宜成为一刀切的检索前阻断器。一个误判会让后面再好的检索也无从补救。可以继续运行便宜的候选检索，再由注入门禁允许零输出。

借鉴 Self-RAG 的分解，注入前标注：

- `need`：当前问题是否需要存储中的历史信息？
- `relevance`：候选是否直接回答或约束当前任务？
- `incremental`：是否补充了当前可见上下文缺少的信息？
- `validity`：是否仍有效、无未解决冲突？
- `budget`：保留多少条和多少 token 足以完成任务？

输出至少区分 `inject`、`omit`、`uncertain`。不能为了填满 top-k 把不相关候选送入模型。

### 5.2 什么叫“有用”

相关、被引用、任务成功是不同证据。知识提供了正确项目约束但任务仍因网络失败，不代表知识无用；任务恰好成功但没有用到知识，也不能算该知识带来成功。

推荐分两层评估：

1. 注入判断：人工标注是否有助于这轮回答、是否冗余、是否冲突。
2. 实际用途：回答是否落实了具体偏好/约束，或有可检查的行为结果；对照运行才用于估计整体任务收益。

如果 Adapter 看不到完整当前上下文，不能声称已确定内容不重复。将这个信号记为 unknown，仅依据可见轮次判断。

## 6. 第三层：LFHV、归档恢复和淘汰

### 6.1 当前实现的准确边界

核对 `governance.py`：影子检索默认 top-k=8，包含 archived、关闭扩展；记录命中次数和排名。默认 `lfhv_resurrect_threshold` 为 1，显式调用恢复治理时可将满足条件的 archived 恢复为 active。它不是每轮召回自动复活，quarantined 也不在这一路检索中。

报告已说明相关统计不能证明任务成功损失，但一些内部命名和恢复理由仍把影子命中称为 false kill。因此优化重点是补足证据，而不是把阈值从 1 改成 3 就称为更智能。

### 6.2 三类判断，避免强行二分

| 归档条目的判断 | 可用证据 | 动作建议 |
| --- | --- | --- |
| 有恢复价值的候选 | 新需求相关，原依据仍有效，当前活跃知识没有覆盖 | 进入恢复评估；先离线或影子验证，再有限恢复 |
| 有明确降值依据 | 已替代、已过有效期、已证伪或用户要求移除 | 停止正常使用；按删除/保留规则处理，不因热度恢复 |
| 尚不确定 | 没有足够相关需求或验证机会 | 低成本保留，受容量和期限管理；不能标成已证明无用 |

### 6.3 借鉴 ARC 与 TinyLFU 的方案

- **记录有限的淘汰历史**：保留摘要、归档原因、版本、时间和命中统计，设置条数/字节预算；元数据本身也可能包含私人信息。
- **使用近期机会，而非永久累积次数**：按独立轮次、任务或时间窗去重；重复问同一句不能无限增加价值。需要保留历史审计，但恢复决策可使用衰减窗口。
- **恢复也走准入判断**：活跃容量不足时，比较恢复条目能新增的用途与容量代价，而不是全部重新放回。
- **考虑工作负载变化**：某项目重新活跃时提高该项目恢复检查优先级，不把长期离线期间当成连续失败机会。
- **将遗忘曲线作为基线**：可比较固定 TTL、LRU/最近使用、时间衰减、现有 LFHV 和改进方案，不预设复杂策略一定更好。

知识与缓存不同：缓存可回源取回页面，永久删除的私人经验可能无法恢复。若正文及合法来源均已删除，ghost 摘要不能凭空还原内容，不能让模型补写为“恢复原知识”。

### 6.4 LFHV 建议拆成两个层次

**机会层**：归档内容在新问题上达到相关性门槛，且可能补足当前活跃内容。这只是潜在损失，记录 probe 的范围、采样率和覆盖情况。

**收益层**：在相同任务、上下文与预算下，对比“现有 active 集合”和“加回候选后重新执行同一截断规则”的结果。加回内容会挤掉其他内容，必须保留相同预算，不能通过无限增加上下文获得伪收益。

可观察 `ΔU = U(恢复策略后的回答) - U(当前策略的回答)`。这只是待测定义，U 应来自任务检查或盲评，不用模型自报分数充当收益。单次差异不证明稳定效果；影子未注入时根本观察不到这个量。

### 6.5 定期治理的轻量做法

- 后台分批扫描，按水位和时间预算执行；不放在每轮首 token 前全库处理。
- 保留最小复核窗口与用户固定保留例外；不同原因用不同保留策略。
- 自动永久淘汰需要预先明确的用户策略，先 dry-run 观察，不在本轮研究里启用。
- 归档正文、索引、事件、审计和备份分别计容量；active 数量受控不等于物理库有界。
- 影子探针若只跑疑似漏召回问题，会有选择偏差。增加少量随机审计样本，报告各组结果；没有已知采样概率时，不将样本比例冒充全量比例。

## 7. 可直接讨论的判定样例

以下是设计标注样例，不是系统已经通过的测试。

| 对话或场景 | 保存/采纳判断 | 注入/治理判断 |
| --- | --- | --- |
| 用户：“以后页面默认浅色。” | 可自动采纳候选类型：明确持续偏好 | 页面设计时注入；糖果算术题不注入 |
| 用户：“这次演示先用深色。” | 当前任务状态，不覆盖全局浅色偏好 | 当前演示按新指令；结束后不全局延续 |
| 用户：“MemWeave 候选审核改成一天。” | 项目决策，可纳入自动采纳白名单 | 解释该项目治理时注入；其他项目不能套用 |
| 用户：“是不是所有候选都应该自动通过？” | 问题，不是已确定决策 | 不生成“全部自动批准”的事实 |
| Assistant：“应该是索引坏了。”没有验证 | 不自动采纳根因 | 不能在下次故障中当已知事实 |
| 工具退出码为 0，随后用户说结果不对 | 保存实际观察或待审，不声称任务成功 | 反例阻断经验自动晋升 |
| 天气查询 | 一般不纳入长期库 | 未来天气问题应获取当前信息 |
| 用户明确要求保存某次天气用于旅行记录 | 可保存为带日期的历史事实 | 不能作为未来天气或当前天气注入 |
| Claude 的建议被 Codex 原样复述 | 同来源链，不新增独立确认 | 不能因重复提取提高采纳等级 |
| 同项目命中三条内容相近的知识 | 保留来源，审慎去重 | 选择必要信息，不为 top-k 填满三条 |
| 旧 API 地址被明确的新地址替代 | 建立替代依据，旧事实不再当现行值 | 问“以前地址是什么”可走历史查询；普通调用用新值 |
| 一年前低频项目约束，项目今天恢复 | 不能因长期未使用判错 | 若仍有效且缺失，可列恢复候选 |
| 已归档内容影子命中，但活跃条目已完整覆盖 | 不增加新事实 | 不必恢复；单纯 shadow hit 会高估价值 |
| 已因错误隔离的条目再次高排名命中 | 错误证据仍生效 | 不通过 LFHV 自动恢复 |
| 因一天未审核而隔离 | 未审核，不是证伪 | 可找回复核；不直接套用“错误隔离”结论 |
| 归档正文永久删除，仅剩摘要 | 保留删除事实 | 无来源时不能生成原文冒充恢复 |

## 8. 验证标准：分母与证据必须明确

### 8.1 准入

| 指标 | 定义 | 防止的误读 |
| --- | --- | --- |
| 自动采纳精确率 | 人工判定正确且应长期保留的自动采纳项 / 所有自动采纳项 | 只看自动化率会奖励乱收 |
| 自动化覆盖率 | 自动完成采纳或明确跳过的可评估项 / 所有可评估项；另报自动采纳占比 | 全部留待审不能冒充高质量自动化 |
| 有价值知识漏收率 | gold 应保存但被跳过或丢失的项 / gold 应保存项 | 只看少收不看漏收会奖励空库 |
| 错误自动跳过率 | 被自动跳过但 gold 应保存的项 / 自动跳过项 | 自动采纳精确率不能覆盖另一侧错误 |
| 人工负担 | 每 100 轮产生的待审条数、重复组数、审核分钟数 | “自动通过多”不一定真的省时间 |
| 纠错代价 | 自动决定被撤销的比例与恢复所需操作 | 允许可逆，但不能把纠错成本隐藏 |

### 8.2 注入

| 指标 | 定义 |
| --- | --- |
| 注入精确率 | 被标为本轮有帮助的已注入项 / 所有已注入项；额外报告宏平均 |
| 必要知识漏注入率 | 需要历史知识但缺失必要支持的任务 / 需要历史知识的任务 |
| 无需记忆任务误注入率 | gold 不需存储记忆但仍注入的任务 / gold 不需记忆任务 |
| 过期/冲突注入率 | 注入了已失效或未解决冲突信息的任务 / 可评估任务 |
| 帮助与伤害 | 同任务固定条件下，开启与关闭记忆后成功状态的配对变化；失败原因另记 |
| 上下文代价 | 每轮注入 token、重复 token、被预算挤出的必要信息 |

Recall@k/MRR 衡量候选位置，不能替代这些指标。按固定 k 作分母的 Precision@k 与按实际返回数作分母的注入精确率应分开报告。

### 8.3 归档与 LFHV

| 指标 | 定义/边界 |
| --- | --- |
| 影子机会率 | 被探测查询中出现合格归档恢复候选的比例；标注抽样方式与覆盖 |
| 恢复候选精确率 | 人工/离线检查确认有效且有新增用途的候选 / 全部恢复候选 |
| 恢复后用途 | 恢复项在观察窗内获得逐条采用或验证证据的比例；分开报告两种证据 |
| 恢复净收益 | 相同上下文预算下恢复方案与原方案的配对任务差值 |
| 任务级误淘汰 | 完整有效知识对照可完成、治理后因所需知识缺失而失败的任务比例；需排除随机与其他失败 |
| 冷知识保护 | 低频但 gold 必要信息的保留/恢复表现，单列报告 |
| 恢复抖动 | 同一内容在固定观察窗反复 archive/active 切换次数 |
| 规模曲线 | active+stale、归档正文、索引、事件、审计、备份分别随轮次数的条数与字节 |

“未被选中”不是“无用”的标签。只有相关使用机会出现、输出可评估时，才能累计用途失败证据；未知与缺测单列，空分母显示 N/A。

### 8.4 计时与运行有效性

分别测后台提炼耗时/费用、纯搜索、Adapter、原生 Hook、on/off 配对首 token 差值。报告 P50/P95、样本数、硬件、Python/SQLite、源码摘要、知识快照、缓存状态、调用顺序、并发与数据库路径类型。

API 失败、无输出、格式错误、截断是独立失败类别；不能把“空输出”判为成功拒答，把“模型没调用成功”判为没有可提取知识。背景提炼不阻塞当前回答，但要测知识可见延迟与队列积压。

不要用两组 P95 相减代替逐对差值的 P95。本次没有跑上述效果或性能实验。

## 9. 第一阶段实验建议

### 9.1 100 条作为诊断集

建议先准备 100 个带时间顺序的案例：40 个准入、30 个注入、30 个归档生命周期。生命周期一个案例应包含写入、状态变化、后续查询和预期决定，而不是一条孤立问题。每个案例注明来源 Agent、目标 Agent 与范围，并平衡两个方向。

案例必须包含正例、负例和不确定例：用户问题被误当事实、短期指令与长期偏好、引用他人观点、模糊指代、旧值更新、重复回声、同话题无关、用户删除、长期低频重要、归档后被替代等。

这 100 条用于发现策略漏洞与检查标注规则，不足以宣称高可靠产品。开发与盲测按人物/项目/知识来源家族隔离；同一事实的改写不能跨集合。若在这 100 条上调过规则，就不能再把同一批最终成绩当独立测试。

### 9.2 标注流程

先写简明标注手册，再由用户确认一小批边界例子。条件允许时两人独立标注、记录分歧并裁定；仅一人时需明确这一限制。模型可辅助提出理由，不能同时独立生成全部标签、调规则、又独立证明效果。

标签至少含：来源支持片段、语义类型、scope、有效时间、当前上下文、推荐动作、理由、允许的不确定性。用户偏好与产品政策作为政策标签，客观外部事实作为证据标签，不混在一起。

### 9.3 对照设置

- 准入：现有全部候选待审 vs 有证据自动采纳；另用“宽松提取”展示漏收与审核量的取舍。
- 注入：现有检索/注入 vs 新门禁；同一候选池、状态与预算。另保留 no-memory 和 gold-memory 上下界帮助定位检索或阅读损失。
- 归档：不淘汰的有效知识参考库、固定 TTL/LRU、现有 LFHV、改进 LFHV；固定主实验容量，必要时再比较容量曲线。
- 先分别替换一层，确保改善来自哪一层；最后做全流程组合，不能三层同时改后只报一个成功率。
- 带模型的比较固定服务商/模型设置、提示、预算和知识快照，交替或随机顺序，多轮重复；重复同一案例的运行不是独立新案例。统计时优先按案例或来源家族配对/分组。

### 9.4 阈值如何确定

不存在有出处的“置信度大于 0.8 就应该自动通过”。在校准集上画自动覆盖率—错误率曲线，选择用户可接受的风险与审核量，再冻结规则到独立测试集。

如希望将错误自动采纳率控制在 2% 以下，这是**产品目标示例**，不是本次结论。即使 100 个独立自动采纳样本全部正确，一侧 95% 二项上界仍约为 2.95%；约需 149 个独立同分布、零错误的自动采纳样本，才有机会将该上界压到 2% 以下。100 个总案例中自动采纳项更少，不能用总样本数冒充这个分母；相关案例和环境漂移会进一步限制结论。

延迟目标同样需要用户认可并由实际客户端对照确定，不能把当前受控搜索的十几毫秒直接当首 token 保证。

### 9.5 建议的首轮验收条件（待确认的工程标准）

1. 越权范围、已删除/已明确否定内容被正常注入、模型猜测被写成已验证事实等边界测试必须通过；在这些测试上零错误不等于证明全场景零错误。
2. 同时报告自动采纳精确率、自动覆盖率、错误跳过率与人工时间，不能靠全部不采纳取得漂亮精确率。
3. 减少误注入时，必要知识漏注入不得超过预先约定的容忍差值；差值在看盲测结果前确定。
4. LFHV 改善需体现相同容量/上下文预算下更少任务损失或更少无效恢复，不能只报恢复次数上升。
5. 真正客户端额外等待需配对测量。后台队列没有无限堆积，物理库增长有明确曲线。
6. 样本不足、缺测或不确定区间过宽时，结论写“证据不足”，不写“没有下降”。

## 10. 推荐实施次序与差异点

先定义决策记录和标注案例，再做窄类型自动采纳与注入门禁，之后深化 LFHV 的机会层和收益层。先做可解释规则基线，有足够真实标注后再评估小模型或统计校准；此时引入复杂算法才有比较对象。

建议每次决定保存 action、reason_codes、source_evidence、scope、validity、policy_version、decision_time；没有校准时不把任意 confidence 字段解释为概率。提供撤销与人工修正，后台再吸收修正记录。

可能形成的项目特色是：同一证据链贯穿“自动准入—按需注入—可恢复淘汰”，三层各自承担不同错误成本，并用真实纠错调整策略。Ghost cache、遗忘曲线、拒绝判断和相关性过滤均有先例；差异需要由跨 Agent 场景下的实现和效果证明，不能仅靠重新命名。
