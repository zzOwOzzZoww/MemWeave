# MemWeave 检索流水线重构与验证记录

日期：2026-09-24

## 1. 结论与范围

检索流程已拆分为“候选生成 → 扩展 → 仲裁 → 截断”。bridge、sibling、anchor 采用同一 stage 协议，保留默认召回行为，显式定义级联关系。全索引词频采用有界 LRU 缓存，记录写入在同一事务内更新版本，查询按版本读取缓存。

核心继续只使用 Python 标准库，无新增向量库、模型服务、Web 或 MCP 依赖。运行中的本地 Runtime 已更新，访问地址保持不变。数据库升级前已在本机临时目录建立 SQLite 一致性备份。

本轮没有修改整体 UI、Hook 安装配置或调用付费模型。实验使用临时副本，未向真实知识库写入实验知识。

## 2. 四层职责

```text
query + project + lifecycle + policy
                  │
                  ▼
候选生成：FTS5 / BM25 → 稀有标识词初排 → 候选池
                  │                     LIKE 兜底候选
                  ▼
扩展：BridgeStage → SiblingStage → AnchorStage
      只返回新增 Candidate，不修改前一路候选
                  │
                  ▼
仲裁：去重、合并 provenance、直接候选保护、扩展位置
                  │
                  ▼
截断：主结果 limit + anchor slack
                  │
                  ▼
ReuseStore：字符预算 → 上下文 + 注入/未注入审计
```

| 层 | 实现 | 负责什么 | 边界 |
| --- | --- | --- | --- |
| 候选生成 | store.py / _generate_candidates | 生成相关候选池、状态与项目过滤、稀有词初排、LIKE 兜底 | 不做最终数量截断 |
| 扩展 | retrieval_pipeline.py / expand | 三路追加候选，携带来源、父记录和深度 | 不删除或重排输入池 |
| 仲裁 | arbitrate / primary_order | 合并多路路径、去重、决定相对位置 | 保留主结果与 anchor 追加结果的区别 |
| 截断 | truncate + ReuseStore.start | 数量预算、字符预算、记录未输出原因 | 不把检索到等同于注入，更不等同于实际使用 |

为了保持既有主题推断，候选层仍保留初始稀有词排序。仲裁层负责跨路组合排序。AnchorStage 会计算最终主结果的只读视图以确定排除集合和剩余预算，但不会截断总候选池；这与旧算法的触发条件一致。

LIKE 兜底只在直接候选为空时准备，且仅在所有扩展仍未产生结果时输出。

## 3. 统一 Stage 协议

```python
class ExpansionStage(Protocol):
    name: str

    def expand(
        self,
        context: StageContext,
        candidates: tuple[Candidate, ...],
    ) -> StageResult: ...
```

StageResult 包含 additions 和 skipped_reason。Candidate 包含：

- row：候选记录；
- origin：direct / bridged / sibling / anchored；
- parent_id、parent_title、parent_origin：推断父记录信息；
- depth：扩展深度。

诊断信息和 trace 内保留技术标识；正常对话继续只允许展示来源 Agent 标签。

默认策略：

```python
RetrievalPolicy(
    stages=("bridge", "sibling", "anchor"),
    sibling_seed_origins=("direct", "bridged"),
    max_depth=2,
    slack=2,
)
```

stages 是启用集合，不是可任意重排的执行顺序。执行始终为 bridge → sibling → anchor。配置当前在 Core 的 Python 接口暴露，未额外增加 UI 开关。

| 扩展 | 触发与输入 | 输出 | 可否触发其他扩展 |
| --- | --- | --- | --- |
| bridge | 直接候选不足 limit；读取既有词共现图 | bridged，depth=1 | 默认可成为 sibling 种子 |
| sibling | limit≥2，合格种子数≥limit；父种子 depth 小于 max_depth | sibling，depth=parent+1 | 不递归生成下一轮 sibling |
| anchor | 按稀有 query 词查找主结果之外的记录 | anchored，depth=1 | 最后执行，不再触发其他扩展 |

将 sibling_seed_origins 改为 ("direct",) 可禁止 bridge → sibling。max_depth=1 允许 direct → sibling，但禁止 bridge → sibling。max_depth=0 关闭所有扩展。

expand_siblings=False 保持旧接口语义：关闭所有扩展，包括 bridge 与 anchor。治理层的反事实测量继续使用这一行为。

## 4. 仲裁、来源与预算

- 主候选为 direct + bridged，保留既有顺序；前 ceil(limit/2) 个候选优先，其后插入 sibling，再接剩余主候选。
- anchor 只在主结果后补充，默认最多超过 limit 两条，不挤掉已经确定的主结果。
- 多路命中同一记录只输出一次，provenance 保留全部进入路径。
- 兼容旧来源口径：被 anchor 再次找到的 bridged 记录，主 origin 仍为 bridged，附加路径另记。
- 数量截断记录 row_budget；已有结果时不使用的兜底记录记 fallback_not_needed。
- ReuseStore 的字符预算仍为既有策略；超预算项记 context_budget。新增 provenance 和 omitted_reason 不进入给模型的正文。

修复了一处实际缺陷：sibling 的父候选被最终数量截断后，旧上下文可能只显示空的 topic=。现在候选携带 related_title，输出时可补全主题。

补全标题会占用少量已有字符预算；极端卡预算的输入可能因此少注入一条，仍不能越过预算。本轮 160 个查询未出现注入记录变化。

## 5. 词频缓存与一致性

### 5.1 缓存对象

缓存全 FTS 索引的有界文档频次。统计到 ceiling+1 即停止，与现有“是否超过阈值”的判定一致。保留 FTS MATCH 的短语、大小写、连字符等原有语义。

不缓存最终候选或检索结果，不缓存原始会话。词频口径继承旧实现：统计全索引；项目、scope 和生命周期过滤在候选 SQL 上独立执行。此缓存不改变可见性控制。

键包含：

```text
数据库绝对路径 + 数据库身份 + 事务 epoch
+ 统计口径标识 + ceiling + 原词
```

进程内共享缓存，跨 KnowledgeStore 实例复用。上限 2048 项，估计权重预算 512 KiB，LRU 淘汰。512 KiB 是缓存权重估计预算，并非进程 RSS 的硬上限。RLock 保护多线程容器操作。

### 5.2 写时失效

retrieval_revision 为单行表，存数据库 identity、随机 epoch、revision。以下记录操作由 SQLite trigger 在同一事务内更新 epoch：

- 插入、删除 knowledge_records；
- title、content、search_terms、status、scope、project_key 的实际变化。

hit_count、last_hit_at、verified_count 更新和召回日志不会改变词频，因此不清空缓存；排序仍每次从数据库读取这些字段。

rebuild_search_index() 在同一事务内重建 FTS 并更新 epoch。随机 epoch 防止事务回滚后整数 revision 重用导致错误缓存命中。

搜索以显式读事务开始，版本、词频和候选来自同一 SQLite 快照。跨进程写入提交后，下次查询读取新 epoch，旧缓存自然失效；旧项仍受 LRU 容量限制。

### 5.3 有意保留的边界

- 采用“首次查询懒计算 + 缓存 + 写时失效”，不是每次写入预计算所有可能短语；冷缓存仍会计算词频。
- sibling 的频次依赖本次候选池，不能直接换成全库 df，继续现场计算，以免改变相关性。
- anchor 的 query 词选择依赖当前输入，仍在查询时执行，但复用缓存 df。
- 词共现图在已有写路径维护；图查询没有结果缓存，重建图后直接读新图，不需要清除 df 缓存。
- 支持通过记录写接口及 rebuild_search_index 更新索引。绕过这些路径直接修改 FTS 虚拟表或替换数据库文件，不属于普通写入契约；维护工具必须调用显式失效或重建接口。
- 冷启动的 Hook 独立进程不能跨进程共享 Python LRU；常驻 Runtime 内可复用。数据库 epoch 能跨进程传播失效。

## 6. 可观测性

KnowledgeStore.search 新增 retrieval_diagnostics，含：

- 各阶段耗时、输入/新增/输出数、跳过原因；
- 启用的扩展、种子来源策略和深度；
- 词频 cache hits / misses / batches / revision；
- 数量预算与兜底未使用原因。

复用 trace 的每个 item 增加 provenance 与 omitted_reason。诊断字段通过现有本地搜索 API 返回，不额外建一张无限增长的流水表。现有复用日志保留策略不变。

后续可据此区分：没有候选、扩展未触发、仲裁后掉出数量预算、超过上下文预算、已注入但未被实际使用。

### 7.2 重构前后对照

冻结旧检索调度与上下文发射逻辑作为测试 oracle：

- tests/fixtures/retrieval_before_stages.py
- tests/fixtures/reuse_before_stages.py

同机、相同初始数据库，旧版 / 新版冷缓存 / 新版热缓存对照：

- 标准 100 查询，3 轮；
- 本地快照 60 查询，3 轮；
- 共 480 个查询轮次；三个版本各执行 480 次计时检索，热缓存预热不计入。

结果：

| 指标 | 标准用例 | 本地快照 |
| --- | ---: | ---: |
| 召回顺序及 origin/related_to 差异 | 0 | 0 |
| 实际注入记录差异 | 0 | 0 |
| 预期主题标题补全（含3轮） | 33 | 72 |
| 非预期上下文差异 | 0 | 0 |

标准集有 90 个正例、10 个负例。重构前后 Recall@3 和 MRR@3 均为 1.0，负例注入率均为 0。每个正例只标一个目标，固定分母为3的 Precision@3 为 0.3333；不能据此判定其他返回项一定不相关。本地快照没有人工 gold，只用于行为等价和耗时对照。

这些数据证明当前回归集没有因重构丢失既有命中，不能证明任意实际任务成功率、全领域相关性或模型回答质量。

### 7.3 检索耗时

冷/热仅指 df 缓存，不是操作系统页缓存。

| 查询集 | 旧版 P50 / P95 | 新版冷缓存 P50 / P95 | 新版热缓存 P50 / P95 |
| --- | --- | --- | --- |
| 标准100条 | 4.507 / 7.702 ms | 4.431 / 8.637 ms | 3.785 / 6.552 ms |
| 本地60条 | 5.733 / 6.765 ms | 5.776 / 6.784 ms | 5.296 / 6.075 ms |

预热后两组实验中的 df 缓存 misses、统计 batches 均为0。热查询 P50 改善约 0.44–0.72ms；冷路径总体接近，部分 P95 有波动，不能宣称所有请求都提速。

| 路径 | 旧版 P50 | 新版 P50 |
| --- | ---: | ---: |
| Codex HTTP recall | 41.015 ms | 30.120 ms |
| Claude Code HTTP recall | 45.676 ms | 46.271 ms |

## 10. 下一步依据

本次将组合行为变成了可配置、可回归验证的契约。今后修改召回算法，先跑单路、级联、预算和范围矩阵，再对照真实失败查询的 gold；不再只检查“搜到了几条”。

性能上应按阶段及完整 Hook 分别定位。当前缓存收益不足以解释历史500ms；后续需要捕获慢请求中进程启动、Runtime初始化、SQL和日志写入的实际分项耗时，避免继续优化已经只有几毫秒的局部。
