# LLM Wiki 机制吸收设计

## 目标

MemWeave 吸收 LLM Wiki 的“编译时知识整理”思想，但不依赖 Obsidian，也不把 Markdown Wiki 作为框架核心。框架继续聚焦多 Agent 共享、证据追溯、生命周期治理和实际复用验证。

## 已吸收机制

| LLM Wiki 思想 | MemWeave 实现 |
|---|---|
| raw 层不可修改 | `agent_events` 保存脱敏后的原始工具事件，SQLite 触发器禁止更新和删除 |
| wiki 是编译产物 | `Knowledge Compiler` 将原始轮次提炼为 `MemoryRecord` 候选 |
| 增量编译 | `source_hash + compiler_version + schema_version` 形成 `manifest_hash` |
| 来源可追溯 | `knowledge_compilation_links` 与 `knowledge_event_links` 构成来源链 |
| 人类保留判断权 | 候选仍经过客观证据或人工审核后才能成为 Active |
| 健康检查 | 沿用生命周期、LFHV、隔离、过期和复用证据指标 |

## 没有直接照搬的机制

### Obsidian 文件结构

MemWeave 的 Core 继续使用 SQLite WAL 和 FTS5。Markdown 或 Obsidian 可以作为可选导入导出 Adapter，不能成为 Agent 共享知识的必需依赖。

### 全局 hot.md

全局热文件容易将某个项目或会话的上下文污染到其他任务。后续只考虑带项目作用域、TTL、容量上限和相关性门槛的 Hot Set，并通过延迟、Token 开销和任务成功率实验决定是否启用。

### 自动联网补全

外部搜索材料不能自动进入 Active 知识。若后续增加研究 Adapter，联网结果只能作为 Raw Source，必须保留 URL、时间和内容 hash，并经过候选与审核流程。

## 当前数据链

```text
Claude Code / Codex 原始会话
  → Transcript Adapter
  → 不可变 AgentEvent
  → CompilationIdentity
  → DeepSeek 提出候选
  → MemoryRecord(candidate)
  → 客观测试或人工审核
  → MemoryRecord(active)
  → FTS5 按需召回
  → ReuseTrace 验证实际使用结果
```

## 下一阶段实验

1. 给知识增加显式的 `supersedes / conflicts_with / derived_from` 版本关系。
2. 对同一主题的多条候选执行合并建议，但任何覆盖操作必须可审计和回滚。
3. 实现有界 Hot Set，对比关闭和开启状态下的首 token 延迟、注入字符数、任务成功率与无关召回率。
4. 扩展知识健康报告，统计无来源知识、孤立知识、冲突知识、长期零命中知识和 Schema 漂移。
5. 在 DPI 垂直任务集中评测“原始日志检索”和“编译后流程知识检索”的效果差异。
