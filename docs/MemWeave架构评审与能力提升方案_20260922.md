# MemWeave 架构评审与能力提升方案

日期：2026-09-22
评审对象：MemWeave（Runtime v0.4.0）
方法：**源码静态核查 + 本轮 5 个实测实验**（live_100 / value / learning curve / 检索判别力 / bad memory）
证据等级：标注 `[实测]` = 有跑出来的数字；`[核查]` = 读源码确认存在/缺失

---

## 0. 一句话定性

**MemWeave 是一个「写入端严格、读取端单薄」的系统。**

写入端它比同类框架（Hermes）更严——有证据门控、有状态机、有精确去重；
但它宣称的核心能力「生命周期治理」**只实现了「晋升」和「隔离」两个方向，缺「过期」和「淘汰」这一整半**，
而这半个方向恰好是它相对"只加不减"方案唯一的卖点。

**最锋利的一处证据**：`live_100` 的 `conflict_and_staleness` 类别 10 条题里，
**前 5 条把旧记录构造成 `state="active"`**，靠 `revision="SUPERSEDED revision 1; do not use this revision"`
这段**写进知识正文的文本提示**让模型避开。`[核查]`
→ **框架在"过期治理"这条关键路径上完全缺位，能力由"把提示写进内容"替代。**
→ 所以这个类别"全过"**不能证明治理能力**，只证明模型会读英文提示。

## 2. 不足清单（三级）

### A 架构级

**A1. 生命周期"只进不出"——核心能力名不副实** `[核查]`

状态机只有 `candidate → active → quarantined`（§5），**没有时间维度、没有容量维度**。
一条 5 年前的知识和昨天写的知识在库里地位完全相同，只要没被 rejected 就永远 active。
- 后果 1：库无限膨胀，检索候选集里噪声比例单调上升
- 后果 2：**没有"遗忘"就没有"资源再分配"**，而这正是这个项目立论的痛点②
- 后果 3：§8 承诺的「知识净增长速度、过期比例」两个指标**无法计算**

**A2. 读取端只有一层字面检索** `[实测]`

`search()` = FTS5/BM25 + LIKE fallback，没有向量、没有重排、没有冲突仲裁。
本轮实测出**三次独立退化**：

| 退化 | 现象 | 状态 |
|---|---|---|
| 同构语料判别力崩坏 | 20 条同构知识共库后 top-3 命中从 100% 塌到 30% | ✅ 已修（稀有判别词优先，6/20 → 20/20） |
| 同族冲突无仲裁 | 正确/错误两条同族记录一起被 pin，排序退回 BM25，坏知识暴露率 **100%** | ❌ 未修 |
| 证据强度不参与决策 | `confidence` 对验证次数不敏感，context 不输出 `verified_count` → 证据 3:1 时伤害仍 20% | ⚠️ 半修（已暴露计数 → 0%，但排序层仍是 BM25 优先） |

**最危险的不是退化本身，而是它「静默」**：检索错了不会报错，agent 拿着错知识或空手自信作答。
**目前没有任何指标能在线上提前发现判别力崩溃。**

**A3. 评测资产与框架代码耦合** `[核查]`

- 356 行的 `live_benchmark.py` 硬编码在 `src/` 里（框架包内），而 `evaluation.py` 只有 79 行
- 后果 1：换任务集要改框架源码，评测无法独立演进
- 后果 2：**评测类别与实现能力不对应**（见 A1 的 `conflict_and_staleness`）——这是比代码缺陷更严重的问题，因为它让所有数字失去可解释性
- 后果 3：ground truth 全靠自建，没有外部对照集

### B 模块级

**B1. `confidence` 语义缺陷** `[实测]`

`confidence = verified / (verified + rejected)`：**验证 1 次和验证 100 次都得 1.0**。
实测：正确/错误知识证据强度 3:1 时，**该字段提供的区分力为零**，伤害仍有 20%。
- ⚠️ 但**它被 4 项单元测试以精确数值钉住**（1.0 / 0.5 / 0.667）→ 是**有意固化的契约**，不是疏漏
- 结论：改它必须连测试一起改，属于**契约重构**而非 bugfix
- 当前缓解（已做）：只把 `verified=N rejected=N` 暴露给模型 → 伤害 20% → **0%**

**B2. 冲突检测完全缺失** `[核查]`

只有 `content_hash` 精确去重（内容逐字节相同才拦）。
**语义等价但表述不同的知识、以及互相矛盾的记录，都能同时进 active，检索层无法仲裁。**
实测后果：坏知识暴露率 100%，两条都进 top-3，**模型只能靠自己判断**。

**B3. Runtime 在 Stop hook 里同步完成 learn** `[核查]`

架构文档 §4 明确「结束阶段**同步**完成」，learn 内部要调 DeepSeek reviewer（网络调用）。
- 后果：**阻塞用户会话结束**
- Hermes 的成熟参照：后台 fork，在自己的 prompt cache 里跑，**从不触碰活动会话**

**B4. 多 Agent 只做到"认证"，没做到"信任分级"** `[核查]` `[实测]`

`daemon.py` 的 21 处 Bearer token 解决的是「**谁在调用**」，
**没有解决「跨 agent 的知识该不该信」**——agent A 写入的知识，agent B 只要看到 active 就无条件采纳。
- 实测印证：bad memory 实验里，我把 `source_agent` 设成 `claude-code-legacy`，
  模型**立刻靠这个标签避开了坏知识** → 说明 source 是模型实际使用的判断依据，**但框架没有对它做任何分级**

### C 工程级

**C1. 合规红线（最高优先）** `[核查]`

`dpi.py`(386 行) + `dpi_sdk_bridge.py`(211 行) + `import_dpi_results.py` + DPI 知识库(424KB)
全部在仓库内，且架构文档 §7 还把「DPI 垂直任务对照集」列为下一步。
**早期仓库混入了特定组织的实验资产，公开前必须整体剥离。**

**C2. 测试覆盖不到真正的风险** `[核查]`

51 项测试**全部是单元测试**，覆盖状态转换、证据门控、API 合约。
**没有一个测试守护检索判别力** —— 本轮两个检索缺陷（判别力崩坏、同族无仲裁）都是**实测才发现**，
如果只跑 pytest，会以为系统是健康的。

**C3. live_100 未重跑** `[实测]`

本轮改了两处（`store.py` 检索重排、`reuse.py` context 渲染）。离线验证过检索集合 100/100 不变、
0 例超预算，但**模型看到的信息变多了**，严格说需要重跑一次 300 次调用才能重新确认 10% / 100% / 100%。

## 3. 创新性方向（4 个，按可立住程度排序）

> 原则：**不要做"加个向量检索"这种抄作业**。创新必须落在"上下文 = 有限公共资源、写入 = 预支开销"这个经济学立论上。

### 创新 1 ★★★ 把「遗忘」变成可证明的收益（LFHV 对照）

- **现状**：所有工作（含本轮 5 个实验）都在证明「**记住有用**」。**没有人证明「忘掉是对的」。**
- **空白**：淘汰机制会不会误杀未来有用的知识？这是"只加不减"方案不敢碰的问题，
  因为答错就等于承认自己在丢资产。
- **做法**：
  - 定义 **LFHV（Lost Future Hit Value）** = 被淘汰的知识在随后 N 轮中**本该命中**的次数
  - 核心指标：**误杀率** = 被淘汰且后续被查询命中的知识 / 全部被淘汰知识
  - 对照实验：同一批任务流，**有淘汰 vs 无淘汰**，同时测「检索判别力」和「误杀率」
- **为什么能立住**：这是**可证伪**的对照——如果误杀率高，说明淘汰策略错了，结论照样成立。
  竞品（AMV-L 的价值驱动淘汰等）只报了淘汰收益，**没报误杀代价**。
- **成本**：低。用现有框架就能做，**不用改核心架构**，只需加淘汰策略 + 埋点。

### 创新 2 ★★☆ 准入定价里包含「检索干扰成本」

- **现状**：Hermes 是「记忆满了报错，逼 agent 自己整理」= 布尔门控；常规做法是 value/cost，cost 只算 token 占用。
- **空白**：一条低质知识的 cost **不只是 token**，还包括**挤占 top-k 名额**
  ——它降低了其他更有用知识的召回机会。这个维度**被普遍忽略**。
- **做法**：`cost = α·token占用 + β·(top-k 占用期望)`
  - β 项可实测：加入 N 条干扰知识后，判别力的下降幅度（本轮已有雏形数据）
- **为什么能立住**：把「检索干扰」货币化，是**新的成本项**，且可测量。

### 创新 3 ★★☆ 证据强度与防伪造耦合

- **空白**：竞品空位（投毒防御 × 生命周期耦合）
- **本轮实测到的软肋**：**若能伪造验证事件，`verified_count` 会反过来变成攻击杠杆**
  ——攻击者用 50 次假验证就能盖过真实知识。
- **做法**：**验证来源加权**（不同来源的验证不等价：人工批准 > 通过的测试 > 同名 agent 自证）
  + 伪造检测（验证事件的来源多样性、时间分布异常）
- **为什么能立住**：把"证据"从计数升级为**带来源权重的分布**，直接回应真实攻击面。

### 创新 4 ★★☆ 把「检索判别力」做成一等指标（方法论贡献）

- **本轮最有价值的发现**：判别力会**静默崩溃**，而且**没有任何现成指标能提前发现**
- **做法**：提出 `top-1 精确率 vs 库规模/同质度` 的退化曲线，作为 memory 系统的必备体检项
- **为什么能立住**：这是**方法论贡献**，能复用到任何 RAG / memory 系统，且不依赖具体实现

## 4. 模块改进方案

| 模块 | 现状 | 改法 | 验证方式 |
|---|---|---|---|
| `store.py` | 844 行，BM25 + 精确去重 + 状态机 | ① 冲突仲裁：同族/同实体冲突时 `verified_count` 提到 bm25 之前；② 加 `kind`/`supersedes` 字段支持版本链；③ 语义冲突检测（可先用规则+embedding 兜底） | 判别力回归测试 + bad-memory 复测 |
| **新增 `governance.py`** | **不存在** | 生命周期"淘汰"半环：`active → stale → archived`，按 `last_hit_at` / `hit_count` / 容量压力驱动；**永不删除**，只归档 | LFHV 误杀率 + 库增长率曲线 |
| `reuse.py` | context 渲染 | ① 已加 `verified/rejected`；② 冲突时显式标注「本族存在 N 条冲突记录」 | 冲突场景复测 |
| `claude_learning_adapter.py` | learn 同步阻塞 | 后台 fork（照 Hermes：不触碰活动会话） | Stop hook 耗时 P95 |
| `live_benchmark.py` | 硬编码在 `src/` | 抽出为 `benchmarks/` 独立包 + JSON 数据集，框架侧只留加载器 | 换任务集不改框架源码 |
| **新增 `metrics.py`** | §8 指标无实现 | 实现知识净增长速度、过期比例、判别力曲线、越权拦截率 | 每轮评测自动产出 |
| `daemon.py` | Bearer token 认证 | 加来源信任分级（agent 分级 + 验证来源加权） | 跨 agent 投毒场景复测 |
| `dpi*.py` + DPI 数据 | 在仓内 | **整体剥离到独立私有仓** | 公开仓 grep 无 DPI 痕迹 |

## 5. 优先修复项（排序）

### P0 · 合规剥离 `[必做，不做则后续全部无意义]`
- **为什么第一**：不剥离，这套东西既不能开源、也不能写进简历、更不能给导师看。
  其他所有改进都会被这一条卡死。
- **范围**：`dpi.py` / `dpi_sdk_bridge.py` / `import_dpi_results.py` / `data/dpi-*` / 文档里的 DPI 章节
- **验收**：公开仓 `grep -ri dpi` 只剩无关词

### P1 · 生命周期「淘汰」半环 `[核心能力缺口]` — ✅ 已落地 2026-09-22
- **为什么第二**：这是宣称能力与实际实现的**最大落差**，也是唯一的卖点。没有它，MemWeave 相对
  「记事本 + FTS5」没有本质区别。
- **范围**：新增 `governance.py`；实现 `active → stale → archived`；接上 `last_hit_at` 埋点
- **配套**：创新 1 的 LFHV 对照实验（同一批工作量，顺手就做了）
- **验收**：误杀率 + 库增长率曲线 + 判别力不随库增长而崩坏
- **落地结果**：`governance.py` + `lifecycle_audit` / `shadow_hits` 表 + `store.transit/mark_hits`
  + `/v1/governance/{report,sweep,resurrect,lfhv}` 四个端点；新增 14 项测试。
  详见 `MemWeave生命周期治理落地_P1P2_20260922.md`。
  **过程中查出两个真 bug**：① `ORDER BY 0` 被 SQLite 当列序号 → 语法/范围错误；
  ② 固定标识符重排会抹掉生命周期排序 → **淘汰机制形同失效**（已折叠状态惩罚进重排键）。

### P2 · 检索层冲突仲裁 + 判别力回归测试 `[实测已暴露]` — ✅ 已落地 2026-09-22
- **为什么第三**：这是**已知会造成 100% 暴露、20~25% 任务失败**的活跃缺陷
- **范围**：① `store.py` 冲突时 `verified_count` 优先于 bm25；② 把本轮两个检索缺陷固化成回归测试
- **验收**：bad-memory 的 `poison_active_1v1` 伤害从 10% 继续下降；pytest 新增判别力断言
- **落地结果**：`_pin_discriminative` 分区内 `(状态惩罚, -verified_count, BM25序)`；
  新增 `test_retrieval_arbitration.py` 3 项——**且每项都先断言"裸 BM25 下确实是坏记录第一"**，
  否则测试在修复前后都能过，等于没测。
  ⚠️ 待办：`poison_active_1v1` 的伤害率**需要重跑**确认下降（本轮只做了检索层单测）。


### P3 · 评测资产解耦 `[数字可信度]`
- **为什么第四**：`conflict_and_staleness` 名不副实这件事说明——**评测错了，所有数字都会骗人**
- **范围**：抽 `benchmarks/` 独立包；**每个类别必须写明它测的是哪段代码**
- **验收**：能一眼看出每个类别对应哪个模块的能力

### P4 · Runtime 异步化 `[体验，非正确性]`
- Stop hook 不再阻塞；learn 走后台队列
- **验收**：Stop hook P95 降到本地写盘量级

### P5 · `confidence` 契约重构 `[需要连带改测试]`
- 改成对证据量敏感（如 Laplace 平滑）+ 同步更新 4 项断言
- **为什么最后**：本轮已用「暴露计数」绕过了它，收益边际递减；
  且它被测试钉住，改动成本与风险都高于前四项

## 6. 预期能力提升方向

| 能力 | 当前 | 目标 | 测量方式 |
|---|---|---|---|
| 生命周期治理 | 只有晋升/隔离，**无淘汰** | 完整三态 + 归档可恢复 | LFHV 误杀率、库增长率 |
| 检索质量 | 单层 BM25，判别力会静默崩 | 判别力有指标守护、冲突可仲裁 | top-1 精确率 vs 库规模曲线 |
| 冲突处理 | 只有精确去重 | 语义冲突可检出、可仲裁 | 冲突场景任务成功率 |
| 跨 Agent 信任 | 只认证身份 | 来源分级 + 验证加权 | 跨 agent 投毒复测 |
| 写入成本控制 | 无成本概念 | 定价含检索干扰成本 | 干扰知识下的判别力衰减 |
| 评测可信度 | 类别与实现不对应 | 每类别可追溯到代码 | 类别-模块映射表 |
| 会话体验 | Stop hook 阻塞 | 后台异步 | Stop hook P95 |

## 7. 与 10-12 ARR 截稿的现实取舍

**时间**：距 2026-10-12 截稿约 3 周，还要并行 11 月开题。

**建议只做创新 1（LFHV）**，理由：
1. 它是 **4 个创新点里唯一"纯增量、不必改核心架构"** 的——只需加淘汰策略 + 埋点 + 跑对照
2. 它填的是**公认空白**（没人报淘汰的误杀代价），可证伪，审稿人无法用"这是工程改进"打回
3. 它的实验设计可以**直接复用本轮已有资产**（同构任务族、baseline/poisoned 对照范式、评测脚本骨架）
4. 它与 P1（淘汰半环）**是同一份工作量**——写了淘汰机制，顺手就把对照实验做了

**明确不做**：创新 4（方法论）可以作为一个 section 写在论文里，不必单独做实验；
