> 日期：2026-09-22　对应评审文档：`MemWeave架构评审与能力提升方案_20260922.md`
> 变更范围：`src/agent_knowledge_bridge/{governance.py(新), store.py, service.py, daemon.py, contracts.py, claude_learning_adapter.py}`
> 测试：`tests/test_governance.py(新)`、`tests/test_retrieval_arbitration.py(新)`

## 0. 一句话

P2 把「同一实体的冲突记录谁排前面」从 BM25 说事改成**证据说事**；P1 把生命周期从「只进不出」
补成 `active → stale → archived`，并且给淘汰装了**自己的证伪器**——影子探针（LFHV）会持续追问
「被淘汰的这条，如果还在，这两天的查询会不会用到它」，用到就自动复活。

> **后续治理补充（2026-09-22）**：候选队列增加三天审核期限。过期候选进入
> `quarantined` 隔离区，不删除、不自动伪装成有效知识；原文、来源和生命周期审计仍保留。
> 知识清单同时支持关键词、类型、作用域、来源 Agent 和更新时间范围筛选。

## 0.1 知识分层与自动归档边界

`scope` 和 `status` 是两条独立维度：

| 维度 | 值 | 含义 |
|---|---|---|
| 作用域 | `user` | 通用知识，可被不同项目读取 |
| 作用域 | `project` | 只在所属项目上下文中参与召回 |
| 生命周期 | `candidate` | 已提出但尚未通过证据门，默认三天内需要处理 |
| 生命周期 | `active` | 已有客观证据，可进入正常召回 |
| 生命周期 | `quarantined` | 候选超时、被拒绝或存在风险，保留但不进入正常召回 |
| 生命周期 | `stale` / `archived` | 曾经有效，后续按活跃度退出或归档，可由 LFHV 复活 |

因此“自动归档”不是把所有新知识直接设为 `active`。低风险的通用事实仍须有客观证据，
否则会绕过证据门并污染两个 Agent 的共享上下文。自动化只负责分类、计时和隔离，人工只需要
处理真正不确定或高风险的候选。

候选到期由独立的 `Governor.expire_candidates()` 处理。Runtime 启动，以及知识清单、候选队列、
知识总览读取前都会自动执行一次，所以不需要逐条进入页面操作。这个动作只处理过期候选，
不会顺带降级 `active` 知识。旧数据库中没有 `candidate_expires_at` 的候选继续留在待审核队列，
避免升级时静默批量隔离历史数据。

完整生命周期治理仍可通过 `Governor.sweep()` 预览：

```text
POST /v1/governance/sweep
{ "agent_id": "claude-code", "project_key": "claude-codex-mvp", "dry_run": true }
```

返回 `expired_candidates`、`quarantined` 和 `transitions`。确认 active 知识的降级/归档结果后，
再将 `dry_run` 设为 `false`。重复执行幂等，过期记录仍可通过人工反馈或后续治理流程恢复，
不会物理删除。

## 0.2 知识清单筛选

`POST /v1/knowledge/list` 在原有 `status`、`limit` 外支持：

| 参数 | 作用 |
|---|---|
| `query` | 对标题、正文、搜索词、来源 Agent、项目键做参数化模糊匹配 |
| `knowledge_type` | `fact` / `preference` / `procedure` / `decision` |
| `scope` | `user` 通用知识 / `project` 项目知识 |
| `source_agent` | 精确筛选产生知识的 Agent |
| `updated_from` / `updated_to` | ISO 日期或时间范围，结束日期包含当天 |

页面的知识清单提供相同的筛选项，并额外显示候选的“待审核至”日期。前端即时筛选用于交互，
后端参数化查询用于数据量变大后的完整查询，避免依赖页面当前已加载的记录数量。

## 1. 改了什么

### P2 · 检索层冲突仲裁

| 位置 | 改动 |
|---|---|
| `store.py::_pin_discriminative` | 排序键在「命中稀有标识符」的分区内部，从 `BM25 序` 改为 `(状态惩罚, -verified_count, BM25 序)` |

解决的问题是评审里记的那个实测缺陷：同一实体（都含 `ledger-svc`）的两条记录，短的、把 query
用词复述得更密的、却只有 1 次验证的那条会夺冠，而 3 次验证的那条被压在后面。现在验证次数在
分区内优先于 BM25——**证据说事，不说措辞**。

**回归测试**（`test_retrieval_arbitration.py`）不只是断言"好记录排第一"，它**先用裸 BM25
查一遍**并断言"裸 BM25 下确实是坏记录第一"。没有这一步，测试在修好之后和修好之前都能过，
等于没有测试。

### P1 · 生命周期「淘汰」半环

新增 `governance.py`，公开四个动作：

| 动作 | 语义 |
|---|---|
| `Governor.sweep(project_key, dry_run)` | 按策略降级/归档，返回**计划**的转移清单 |
| `Governor.shadow_probe(project_key, query)` | 对一次真实查询问反事实：已归档的记录会不会被服务到 |
| `Governor.lfhv_report(project_key)` | 查询误杀率 + 当前归档记录误杀占比 + 历史影子命中/复活计数 |
| `Governor.resurrect(project_key, dry_run)` | 把误杀的捞回 `active` |

支撑改动：

- **schema**：`knowledge_records` 加 `last_hit_at` / `hit_count`；新表 `lifecycle_audit`（状态转移审计）、
  `shadow_hits`（影子命中）。全部走 `_ensure_column` 增量迁移，老库可直接升。
- **状态机**：`LIFECYCLE_STATUSES = {candidate, active, stale, archived, quarantined}`；
  `stale` 仍可召回但排在 `active` 之后；`archived` 退出常规召回，**永不删除**。
- **`store.transit()`**：唯一的状态写入口，每次都写 `lifecycle_audit`。淘汰＝状态变更，不是删除，
  所以永远可逆、历史完整。
- **`store.mark_hits()`**：注入埋点，接在 `ClaudeLearningAdapter.recall()` 里
  （`emitted_ids` 非空时调用）。**hit 是比 adoption 弱、比检索强的信号**：它说明这条还在被端出去。

### 淘汰策略（`DEFAULT_POLICY`）

| 键 | 默认 | 含义 |
|---|---|---|
| `stale_after_days` | 30 | `active` 连续无「确认性活动」多久 → `stale` |
| `archive_after_days` | 90 | `stale` 且继续沉睡多久 → `archived` |
| `max_active_per_project` | 200 | 活跃集上限，超了按证据强弱降级 |
| `min_active_per_project` | 5 | 容量压力**永不可击穿**的下限 |
| `lfhv_resurrect_threshold` | 1 | 影子命中几次判为误杀 |

两个刻意的设计决定：

1. **`last_activity` 只认三种时间**：被服务（`last_hit_at`）、被独立确认（`verified`
   证据时间）、首次写入。**重新发布同一个 claim 不算**——那说明有人复述了这句话，
   不说明这句话还成立。
2. **两级用同一根绝对时钟**（都从 `last_activity` 起算），不是"降级之后重新计时"。否则
   `stale_after + archive_after` 会叠成 120 天，策略语义和文档对不上。

## 2. 测试过程中查出来的两个真 bug

这两个都不是"测试写错了"，是测试逼出来的实现缺陷，值得单独记：

**(1) `ORDER BY 0` 是非法排序键。** 影子探针需要"像没淘汰过一样排序"，我原本用一个常量表达式
把它置零，SQLite 把裸整数当**列序号**解析（1-based），于是 `ORDER BY 0` 报
`1st ORDER BY term out of range`。同一个 bug 在 LIKE 兜底分支上表现为语法错误
（常量串里多带了一个逗号形成 `,,`）。**教训：拼接 SQL 的 ORDER BY 片段，宁可整个片段省略，
不要用一个"中性值"去占位。**

**(2) 固定标识符重排会把生命周期排序整个抹掉。** SQL 里 `ORDER BY 状态, BM25` 排好页之后，
`_pin_discriminative` 又按 `(是否命中标识符, -verified, BM25序)` 重排——**状态这一维被丢了**。
后果很严重：把一条记录降级成 `stale`，只要它还命中那个标识符，它就会重新爬到 `active` 之上，
**淘汰机制等于完全失效**。修法是把状态惩罚折叠进重排的排序键（`active=0 < stale=1 < archived=2`），
并且给影子探针留 `status_aware=False`。

(2) 是本次最有价值的一条：它说明**「排序是分两段做的」这种结构，天然会吃掉第一段的排序意图**。
任何"先在 SQL 排、再在 Python 排"的检索层都要专门测这件事。

## 3. 时钟统一（顺带修掉的隐藏缺陷）

`mark_hits()` 原本用模块级 `utc_now()`，而 Governor 用注入时钟。测试里把时钟往前推 20 天再打
hit，`last_hit_at` 反而落在"现在"之前 → 规则读起来正确、跑起来错误。

改法：**时间源归 store 所有**。`KnowledgeStore(database_path, clock=utc_now)`，内部所有
`utc_now()` 改 `self.clock()`；`Governor` 不再自带时钟，直接 `store.clock`。
这样不存在"治理层和被治理的记录对不上表"的可能，也让淘汰规则可复现。

## 4.5 ⚠️ 顺带查出的一个会污染所有延迟数字的环境问题

跑回归时发现 `retrieval_ms` p50 = 159ms，而 09-21 基线是 2~4ms——看着像 40 倍退化。
逐层排查结论：**不是代码，是数据库文件所在路径。**

| 同一个 `evaluation.db`、同一份代码 | search p50 |
|---|---|
| 较深的本地工作目录 | **77.3 ms** |
| 系统临时目录 | **1.83 ms** |
| `%TEMP%` | 1.82 ms |

`cProfile` 显示 80ms **全部**花在 `sqlite3.Connection.close()` 上（1.611s / 20 次调用），
跑 SQL 只要 0.46ms。这不是算法开销，是文件系统过滤驱动（同步盘 / 实时杀软）在拦截句柄关闭。

**两条实际影响**：

1. **历史延迟数字之间不可比**。09-21 记的「检索 P95 4.5ms」和今天桌面路径上的「P95 188ms」
   不是同一个世界的数据。要么把库移出同步/扫描目录再测，要么在报告里注明测点。
2. **影子探针的成本被环境放大了 40 倍**。在正常路径上隔离测量（`live_100 --retrieval-only`，
   同库同代码，只切开关）：

   | | recall@3 | 无关注入 | retr p50 | adapter p50 | adapter p95 |
   |---|---|---|---|---|---|
   | `MW_LFHV_PROBE=0` | 1.0 | 0.0 | 3.42ms | 15.63ms | 24.06ms |
   | `MW_LFHV_PROBE=1` | 1.0 | 0.0 | 2.71ms | 13.75ms | 15.02ms |

   **开着探针反而更快** → 说明探针开销**低于本机可测噪声**（另一次单点微测得 +0.4ms）。
   结论：**治理逻辑本身很便宜，贵的是路径。** 09-21 基线（retr p50 3.04ms / adapter p50 10.73ms）
   与本次干净基线（2.71~3.42ms / 13.75~15.63ms）在检索侧一致，adapter 侧的差异落在本机
   运行间波动带内，不能归因于 P1/P2。

顺带把 `shadow_hits` 的建表从 `Governor.__init__` 移进 `KnowledgeStore._initialize()`：
**schema 归 store**，这样构造 governor（每轮可能发生）不再执行 DDL。
