# 候选审核期限调整与验收

日期：2026-09-24。

## 1. 用户规则

待人工采纳候选的默认审核期限由 3 天改为 **1 天，即创建后满 24 小时**。不是自然日零点，也不从本次升级时重新计时。

到期未获批准或合格验证证据的 candidate 进入 quarantined（已隔离）。记录保留，但不参与正常召回、不默认占据待采纳清单；用户可通过 Quarantined 筛选找到记录，再人工批准为 active。到期不是永久删除，也不是 archived 状态。

重复提交相同候选不会延长期限。已采纳记录不受候选待审期限影响。

## 2. 实现与迁移

- `store.py` 的 `CANDIDATE_REVIEW_DAYS` 统一设为 1；新候选写入创建后一天的到期时间。
- `governance.py` 引用同一常量，并在审计原因中记录真实到期时间，避免把自定义期限说成默认值。
- Runtime 启动时先迁移旧默认期限，再执行到期治理。迁移只修改仍为 candidate、原到期时间恰为创建后 3 天的记录；自定义期限、NULL 旧数据和其他状态不改。迁移幂等，不修改知识正文或内容时间戳。
- 到期治理在 Runtime 启动、管理页读取/刷新等现有治理调用中执行，不新增轮询线程，也不在每次召回时扫描迁移。
- 默认待采纳仅显示 candidate；隔离状态单独筛选，页面提示到期可找回。到期展示增加本地时分，清单总数与可见记录一致。

旧数据的 NULL 期限保留原值，治理仍可依据创建时间和默认策略计算到期；不承诺未经过 Runtime 启动的独立旧库也完成显式 72 小时期限定值迁移。

## 5. 取舍

一天期限降低待审积压，但用户一天未处理不代表知识没有价值，因此保留隔离与恢复入口。该改动不能保证物理数据库不增长：隔离正文仍保留，事件、归档、备份等仍需独立保留策略。

下一步应统计候选采纳率、隔离后恢复率、人工审核时间，并结合真实跨 Agent 任务的漏召回、误召回和配对延迟评估。不要用待采纳条数减少替代框架效果提升。
