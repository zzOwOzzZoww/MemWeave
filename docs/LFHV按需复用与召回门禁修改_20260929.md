# LFHV 按需复用与召回门禁修改

日期：2026-09-29。状态：代码及文档已修改；按用户要求，本轮未执行单元测试、集成测试、数据集评测或真实 Agent 验收，也未重启正式 Runtime。

## 1. 本轮要解决什么

原 LFHV 路径在正常召回之后探测 archived，只记录“可能仍有用”，需要之后显式恢复，再到下一次请求才有机会使用。本轮改为 **按需复用、同步复活**：当前请求需要、当前证据合格且有上下文空间，就在本轮输出，并同步恢复为 active。

截图中的首轮诊断分数仍保留：正向证据召回率 30.7%、跨语言召回率 3.3%、近似主题拒答净空率 0%。本轮只根据源码和 calibration 样本定位并修改，不重新运行评分；这些历史数字既不是当前改版的成绩，也不表示问题已全部解决。

## 2. 同一轮如何完成复用和复活

1. 主检索获取 active / stale，经过现有范围、版本、相关性和答案门禁。
2. 还有条数空位时，检查当前项目或 user scope 是否存在 archived。没有则立即跳过。
3. `Governor.prepare_recovery` 运行包含 archived 的检索，关闭扩展，默认 top-k=8；历史查询和显式拒绝使用记忆的请求不自动恢复。记录影子机会，但此时不改变知识状态。
4. 只保留有过采纳证据、当前相关性充分、未隔离、未替代、未冲突、未废止的归档记录。给恢复候选绑定本轮查询摘要、策略版本、正文和检索元数据签名。只填主检索剩余位置。
5. `ReuseStore.start` 计算字符预算，在写锁下重新核对 live 状态、作用域和内容，对即将发出的子集再次检查证据要求。
6. 真正入选的记录通过 `restore_for_reuse` 转为 active，同时更新 `last_restored_at`、生命周期审计、项目恢复统计、复用 trace 和 hit_count。全部使用同一个 SQLite 写事务。
7. 事务提交后返回本轮上下文。Trace 写入异常则连同恢复一起回滚；可选恢复路径异常时，Adapter 尝试回退到原有正常结果。

当知识未进入上下文时，不因为“曾经搜到”就先复活。两个 Hook 竞争同一条记录，后到的一方若发现内容一致且已 active，可以继续使用，但不会再次计为恢复。相同轮次重试复用已有 trace，不重复增加 hit_count。

这里的输出是“框架已生成并提交给调用方的上下文”，不保证网络传输、Agent 实际读取、采纳或任务成功。进程在本地提交后、返回 Hook 前崩溃的窗口，仍需通过同轮重试衔接。

## 3. 证据和统计怎样区分

| 信号 | 表示什么 | 不表示什么 |
| --- | --- | --- |
| shadow hit | 探测时出现合格归档匹配 | 已恢复或已使用 |
| `lfhv_candidate_items` | 进入上下文组装的恢复候选 | 全部发出 |
| `lfhv_emitted_items` | 本轮输出包含的恢复路径记录 | Agent 已采纳 |
| `lfhv_restored_items` | 本事务实际从 archived 改成 active | 每次重复使用都算复活 |
| `lfhv_not_emitted_items` | 因预算、证据变化等未输出 | 知识永远无用 |
| 后续约束验证 / 任务结果 | 单独观察下游表现 | 没有对照就能得出因果收益 |

复用 trace 保留来源与内部审计字段，对话仍只按既有要求展示来源 Agent，不展示内部知识编号。

`MW_LFHV_RECOVERY` 默认 `1`；设为 `0` 保留只观察的旧路径。`MW_LFHV_PROBE=0` 同时关闭自动恢复及影子探测。显式调用 `shadow_probe()` 仍只观察；显式 `resurrect()` 仍按旧治理入口恢复，不增加注入计数。

## 4. 截图中召回问题的源码修改

### 4.1 统一中英文术语，避免候选与证据两套规则

新增 `retrieval_terms.py`，提供有限、可审阅的中英等价术语与英文词形归一。FTS 查询和证据检查共享同一词表。每个概念在证据计数时只算一次，不能把多个同义词当成多份独立证据。

例如 reads / read、writes / write 归一，数据库 / database、事务 / transaction、迁移 / migration 等可以对应。去掉旧版“看到数据库就推测 SQLite/WAL”一类将相关技术当同义词的扩展。专有实体仍依赖名称、项目范围和已保存的检索元数据，不会自动翻译所有项目名。

这是一种有界词法增强，不是通用语义召回。不增加向量库、模型依赖或在线翻译调用；词表之外的深层改写与跨语言表达仍可能漏召回。

### 4.2 旧中文正文能够参与索引

旧索引只为标题和 search_terms 生成中文 n-gram；没有这些元数据、知识只写在中文正文里的记录可能难以检出。本轮将正文前 5000 字符也纳入写时索引，额外 n-gram 最多 1024 项，英文词形补充最多 128 项。

Runtime 下一次启动会按 `bounded-body-terms-v2` 索引版本进行一次事务性重建，并使统计缓存失效；重复启动检查到版本后跳过。独立 SDK 不会在每次 recall 构造 Store 时扫描重建，可在显式维护阶段调用 `rebuild_search_index(only_if_outdated=True)`。本轮没有执行该迁移。

### 4.3 “主题相同”不能替代“回答所需证据”

新增具体数值、实测结果和仅有讨论的指导语检查，作用于有元数据和无元数据的记录，也作用于扩展/fallback 路径。

- 问精确阈值、超时或数量，正文需要有相关的数值及相应事项，不能仅由标题或搜索标签补出答案。
- 问哪个实验结果证明了收益，正文需要有关联的测量描述和数值。建议、假设、示例或未验证说法不能直接作为测量证据。
- 问已经约定的做法，明确只有讨论、没有结论的记录不能充当指导规则。
- 行数截断和字符预算可能移除部分证据，最终输出集合也重新检查，避免中间候选齐全但实际只注入半份证据。

这是局部词法门禁，不证明它已经理解所有问题，也不判断论文或实验结果的真实性。保留正向召回与错误注入之间的权衡，后续必须一起看正向和负向指标。

## 5. 评测工具也要跟随契约变化

冻结的 v1 数据集把 LFHV 类题目定义成“不注入，只影子发现”。直接用该口径评分新版正常行为，会把当轮复用当作错误。

本轮保留 `cases.jsonl` 与原始基线，新增两个显式 profile：

| Profile | 执行行为 | LFHV 评分目标 |
| --- | --- | --- |
| `shadow-v1` | 显式关闭自动恢复 | 不注入；有影子候选 |
| `on-demand-v2` | 启用当轮复用 | 同一条有效归档证据在本轮输出，并实际恢复 |

预测文件和评分器都要使用同一个 profile，混用报错。v2 只在内存中调整 LFHV 类预期，不覆盖原案例或原分数。新增 `lfhv_same_turn_recovery_rate`，同时保留拒答净空率和禁止证据注入率。

Runner 还改为每个案例独立数据库、按目标选择真实 Codex / Claude Adapter、移除包含场景类别的合成标题。缺失预测不再被评分器当成正确拒答；未知、重复的证据引用会报错。原 baseline 运行时实际上共用临时库、靠项目键隔离，说明文字已经补充澄清。

这些 runner 和 profile 变化会影响可比性。后续比较应明确相同 runner、相同 profile、相同切分及代码快照，不能把新旧总分直接当作纯算法增益。

## 6. 待验证清单（未执行）

- 同一轮归档匹配 → 输出 → active；trace、hit_count、last_restored_at 一致。
- 条数和字符预算不足时不提前恢复；正常 active / stale 结果保留优先位置。
- 查询前后删除、正文或元数据修改、替代、冲突、隔离、停用 Agent 等边界。
- 重复 Hook 与两 Agent 并发；恢复失败/trace 写入失败的回滚和正常召回回退。
- 中英文双向查询、无 search_terms 的中文正文、英文词形、主体和作用域隔离。
- 有真实数值和实测证据的正题；只有同主题讨论、无数值、示例数值和假设结果的负题。
- 先 calibration / dev，再冻结修改后运行 test；同时报告两种 LFHV profile，最后复测全量回归。
- 分开记录检索、完整 Hook、首次索引升级耗时及真实任务 TTFT；对照错误注入、任务成功率和总 token。

本轮不报告新的通过数或性能数据。恢复并输出不等于任务成功；增加这一轮的上下文会增加输入 token，是否省下后续重述或试错成本需另做实验。
