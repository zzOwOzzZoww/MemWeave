# MemWeave v0.1 验收记录

验收日期：2026-09-18

在基础互通 smoke 之外，真实 Claude Code ↔ Codex 任务交接、客观验证和反向回执闭环见 [`MemWeave完整Demo验收记录.md`](MemWeave完整Demo验收记录.md)。

## 验收目标

验证两个异构 Agent 不直接复制彼此本地记忆文件，而是通过统一 MCP 协议和统一知识记录完成双向互通：

```text
Claude Code 发布 → Codex 检索
Codex 发布 → Claude Code 检索并反馈
```

## 实现结构

```text
Claude Code MCP Client                 Codex MCP Client
          │                                   │
          │ identity=claude-code              │ identity=codex
          ▼                                   ▼
  agent-knowledge-bridge stdio MCP processes
                       │
                       ▼
             shared SQLite + FTS5
```

两个客户端分别启动独立 MCP 进程，进程身份由客户端配置固定注入。模型不能通过工具参数指定 `source_agent` 或 `requester_agent`。两个进程使用同一个 SQLite 数据库，因此不需要 Claude Code 与 Codex 直接读取对方的专有记忆目录。

## 统一知识字段

当前 `KnowledgeRecord` 包含：

```text
id
title
content
knowledge_type: fact | preference | procedure | decision
scope: project | user
project_key
source_agent
status
adopted_count
verified_count
rejected_count
created_at / updated_at
```

证据独立记录 `agent_id`、`outcome`、`summary` 和时间。相同知识被第二个 Agent 发布时不创建重复正文，而是新增 `confirmed_duplicate` 证据。

## 已验证行为

- Claude Code 身份能够发布，Codex 身份能够检索且返回 `cross_agent=true`；
- Codex 身份能够发布，Claude Code 身份能够检索；
- Claude Code 能对 Codex 来源知识写入 `verified` 反馈；
- 项目级知识不会被其他项目读取；
- 用户级知识可以跨项目读取；
- 精确重复知识自动去重，并保留第二来源证据；
- 未验证知识收到拒绝反馈后进入 `quarantined`，不再参与正常检索；
- 两端发现相同的五个 MCP 工具；
- Claude Code 用户级 MCP 状态为 `Connected`；
- Codex 全局 MCP 状态为 `enabled`。

## 真实 Agent 端到端验收

在自动 smoke 之外，已让 Claude Code CLI 和 Codex CLI 各自通过模型决策调用 MCP，正式数据库保留以下两条验收记录：

| 发布方 | 知识 ID | 唯一检索词 | 另一端检索证据 |
|---|---|---|---|
| Claude Code | `kn_0b2d00ccbb2f4f6f` | `AKB-E2E-20260918-A7F3` | Codex 返回 `source_agent=claude-code`、`cross_agent=true` |
| Codex | `kn_fc77e072f30e48e7` | `AKB-E2E-20260918-B9K2` | Claude Code 返回 `source_agent=codex`、`cross_agent=true` |

验收过程证明了三件事：

1. 两个模型都能根据自然语言要求选择正确的 `knowledge_publish` 或 `knowledge_search` 工具；
2. Agent 身份由各自 MCP 启动配置注入，发布结果中的 `source_agent` 与调用端一致；
3. 另一端读取后能识别这是跨 Agent 知识，并返回 `cross_agent=true`。

非交互 CLI 默认审批策略曾拦截 MCP 调用。首次调用中，模型已生成正确工具参数，但调用没有执行；为本次受控验收启用允许 MCP 调用的运行模式后，同一链路成功。这属于客户端授权行为，不是 Bridge 服务故障。交互式使用时由用户在客户端界面确认即可。

本次 Claude Code CLI 回传的实际模型为 `claude-opus-5`。因此这次验收证明的是框架与 Claude Code、Codex 的互通能力，不应描述为 DeepSeek 模型验收；框架本身不依赖具体模型供应商。

### 默认模型切换后的复验

为控制日常开发成本，本机 PowerShell 中的 `claude` 命令已改为调用 `ccb`，并固定以下运行配置：

```text
Provider: OpenAI compatible
Base URL: https://api.deepseek.com/v1
Model: deepseek-flash
Thinking: disabled
```

切换后，DeepSeek 通过 MCP 检索到正式知识 `kn_0b2d00ccbb2f4f6f`，调用结果的 `modelUsage` 明确记录为 `deepseek-flash`。该次调用使用的 Agent 身份仍是 `claude-code`，所以读取 Claude Code 自己发布的知识时 `cross_agent=false` 是正确结果。`claude-opus` 保留为显式备用命令，日常启动不会再默认使用它。

## 性能基线

一次完整 stdio smoke 的测量结果：

| 操作 | 耗时 |
|---|---:|
| Claude Code MCP 冷启动 | 781.54 ms |
| Codex MCP 冷启动 | 770.05 ms |
| Claude Code MCP 再启动 | 769.52 ms |
| Claude Code 发布 | 6.78 ms |
| Codex 检索 | 4.01 ms |
| Codex 发布 | 5.40 ms |
| Claude Code 检索 | 8.98 ms |
| Claude Code 写入反馈 | 7.57 ms |

冷启动发生在客户端建立 MCP 会话时，连接后的工具调用不会重复启动进程。当前在线检索没有调用 LLM、远程服务或实时 embedding，因此单次调用维持在毫秒级。

## 当前限制

- 自动 smoke 使用临时数据库；真实 Agent 验收的两条知识保存在正式知识库；
- 当前能在明确提示下正确调用 MCP，尚未自动分析完整会话；
- 当前检索是 FTS5 关键词检索，尚未加入 embedding 和重排；
- 当前只有 `project` 和 `user` 两种作用域；
- 当前拒绝隔离策略是保守的最小规则，还没有完整版本图和冲突关系；
- 当前没有后台知识压缩、过期检查和 `ImportGrant`；
- MCP 工具可用不等于 Agent 一定会在正确时机主动调用，后续需要任务集评估调用决策。

## 下一阶段门槛

明确提示下的双向迁移已经通过。进入自动化前，需要建立一组包含“应检索”和“不应检索”的小型任务集，观察：

1. 没有显式工具指令时，Agent 是否能在依赖历史信息的任务中主动检索；
2. 普通问答是否错误调用知识库；
3. 检索结果是否被实际采用；
4. `verified` 和 `rejected` 反馈是否准确对应客观结果；
5. 引入检索后首 token 延迟增加多少。

这些指标成立后，再实现自动会话候选提取、Context Gateway 和通用 Adapter。
