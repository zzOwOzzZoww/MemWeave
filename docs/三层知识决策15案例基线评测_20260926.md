# MemWeave 三层知识决策：15 个案例基线评测

评测日期：2026-09-26。状态：已执行、已复核；有不符合预期的案例，不代表全部通过。

本次已经定位到当前代码的具体不足：普通知识的注入对本轮意图、信息冗余及版本有效性的判断不足；LFHV 会把再次检索命中当作恢复依据，即使知识不适用于本轮，或者已被新决定替代。提炼端能正确处理本轮明确的一次性要求与未决定问题，但出现了从无证据对话扩写通用建议、保存范围不稳定的现象。

这份报告记录修改前的行为。生产 `src/` 未修改，正式 Runtime 未重启，真实知识库未读取或写入。所有数据库与对话都是隔离的合成测试材料。

## 1. 评测设计与证据边界

| 项目 | 实际执行方式 |
| --- | --- |
| 独立场景 | 15 个：准入 5 个、注入 5 个、归档 5 个 |
| 准入观察 | 每场景 × 两个 Adapter × 两次重复，共 20 次 |
| 模型 | 已配置的 `deepseek-flash`，20 次真实调用，无 API 错误 |
| 准入链路 | Claude/Codex 原生会话格式解析 → 当前 Reviewer → 当前入库校验 → 隔离 SQLite |
| 注入观察 | 5 场景 × 两个跨 Agent 方向，共 10 次 |
| 归档观察 | 5 场景 × 两个跨 Agent 方向，共 10 次 |
| 本地复跑 | 注入与归档再执行 20 次；排除耗时后，所有结果字段一致 |
| 输入标签 | 执行前由助手编写并冻结；尚未由用户独立审定 |
| 隔离数据规模 | 每个注入/归档场景只有 1–2 条知识，用于定位逻辑边界 |

准入使用真实模型及生产提示，未替换成固定回答。每次重复使用独立数据库。输入 parser 产物与合成对话逐字比对，没有工具执行事件。

注入与归档使用预先批准的固定知识，独立检验后两层；这些知识不是前一阶段自动采纳的结果。两个跨 Agent 方向验证了来源与目标的路由行为，但 Codex Adapter 继承共享核心，因此不能把它们当作两套独立算法的验证。

本次直接调用 Adapter，没有启动真实客户端、hook 进程或 HTTP Runtime。记录的“注入”指 Adapter 已生成附加上下文且审计轨迹标为 emitted；没有验证客户端实际接收，也没有让下游模型生成答案。因此不据此声称任务回答错误、真实任务成功率提高，或正式客户端端到端链路完全正常。

## 2. 全部案例结果

| 案例 | 场景与预期 | 实测 | 判定 |
| --- | --- | --- | --- |
| A1 | 明确要求记住跨项目浅色主题偏好，目标自动采纳 | 4 次均正确提取 user/preference，均为候选 | 提取正常；自动采纳未支持 |
| A2 | 明确确认青岚项目 24 小时审核期限，目标自动采纳 | 4 次均正确提取 project/decision，均为候选 | 提取正常；自动采纳未支持 |
| A3 | 今天演示使用深色，明确不要长期记住 | 4 次均无候选 | 符合 |
| A4 | 询问是否自动批准，明确没有决定 | 4 次均无候选 | 符合 |
| A5 | 助手无证据猜测超时根因，预期不产生持久候选 | 4 次均生成“先取证再排查”的建议候选，范围在 user/project 间变化 | 不符合冻结标准；存在政策讨论空间 |
| B1 | 询问页面长期主题偏好，应注入浅色 | 两方向均注入正确偏好 | 符合 |
| B2 | 浅色/深色物体吸热物理题，明确无关页面偏好 | 两方向仍注入页面主题偏好 | 不符合 |
| B3 | 另一项目询问期限，不得套用青岚项目配置 | 两方向均零注入 | 符合 |
| B4 | 只问当前期限，应仅注入新 24 小时 | 两方向均注入旧 72 小时与新 24 小时，旧条在前 | 不符合 |
| B5 | 提示已提供期限且要求不重复，只解释 SQLite WAL | 两方向仍注入期限 | 不符合 |
| C1 | 有效归档知识是所需信息，恢复后应可召回 | 两方向均先不注入，影子命中，显式恢复后注入 | 符合机制预期 |
| C2 | 无关物理题重复命中归档页面偏好，不应恢复 | 两方向均累计 3 次命中，显式恢复后注入页面偏好 | 不符合 |
| C3 | 当前 24 小时已可回答，不应恢复已废止的 72 小时 | 两方向均恢复旧值，之后新旧一起注入 | 不符合 |
| C4 | 已驳回、处于 quarantined 的记录不得恢复 | 两方向均保持隔离，无恢复 | 符合 |
| C5 | 365 天无查询不等于错误；另检查归档保留策略 | 保持 archived、命中 0；治理 sweep 未扫描这条归档记录 | 未误删；长期归档淘汰能力缺口 |

主运行 40 次观察的机械核对为：18 次符合、14 次不符、8 次自动采纳未支持。按独立场景看，为 7 个符合、6 个不符、2 个自动采纳未支持；C5 同时记录一个长期治理能力缺口。

这些数字不是框架总体准确率。案例是定向合成的边界诊断，标签尚未独立审定，重复次数也不足以估计模型行为分布。

## 3. 准入：需要约束来源，也要区分能力缺口

A1/A2 说明当前提炼器能够识别明确偏好、项目决策及范围。未自动采纳是当前普通知识的安全策略，不应描述成提取失败，也不能据此直接开启所有候选自动批准。

A5 输入只描述一次超时，助手承认“SQLite 索引损坏”只是没有证据的猜测。实际候选没有把索引损坏写成已证实根因，而是变成“没有证据不要下结论”的通用排查规程，并增加服务日志、CPU/内存/连接池、近期变更、链路追踪等来源中未执行或验证的步骤。

这暴露了两个更准确的问题：

- 保存的内容从会话观察延伸成了模型的一般建议，缺少逐项来源约束。建议未必错误，但不是这次实际验证出的经验。
- 同一语义输入的保存范围不稳定：两个 Adapter 均在一次运行中给出 project，另一次给出 user。

若产品允许“未经验证的通用建议”进入候选，A5 应独立分类，而不能简单标为错误知识。本轮保留执行前“不生成持久候选”的标准，不在看到结果后修改答案。4 条内容均仍是候选，没有自动成为 active；人工门禁有效。

代码依据：`claude_learning_adapter.py` 的 `_persist_proposal` 检查结构、类型、scope 枚举与敏感信息；普通提案没有逐句来源蕴含校验。具备失败→成功工具证据的结构化经验另有自动晋升路径，普通偏好/事实/决定仍等待审核。

## 4. 注入：相关词命中不等于当前需要

B2 是最直观的反例：即使用户明确说这是物理题，与页面偏好无关，页面主题知识依然以 direct 来源进入附加上下文。问题出现在直接候选上，不能全部归因于 bridge/sibling 等扩展路径。

B5 则表明，已经在提示中完整提供且当前问题不需要的事实仍会重复注入。仅优化排序不足以判断“这条信息是否为本轮增加帮助”。

B4 特意构造新旧记录同时 active 的状态滞后情形。旧正文已明确写明废止，新正文也说明替代关系，系统仍把两条都交给下游。这不证明模型一定回答 72 小时：模型可能正确理解正文；它证明过滤与仲裁层没有阻止已知过时材料占用本轮上下文。

代码依据：`experiences.py:86` 的 `filter_rows` 对结构化经验检查适用条件，普通记录直接保留；`reuse.py` 的 `start` 对普通记录主要沿用预算与结构判定，并另做状态/scope 复查。本轮暴露的是普通知识的意图、冗余与有效性门控不足，而不是不存在任何适用性检查。

## 5. LFHV：影子命中不等于误淘汰

C1 验证恢复机制确实可用，但 C2/C3 暴露恢复资格过宽。

C2 中，同一句无关物理题执行三次影子探测，计为三次命中；调用恢复后，页面偏好变回 active，并进入同一物理题的上下文。当前默认恢复阈值是 1，因此不能说“第三次才触发恢复”。三次重复说明统计未区分独立使用机会；词面无关内容可以被恢复是另一个问题。

C3 中，恢复前当前 24 小时已经被注入，旧 72 小时在影子检索中排第二仍获得恢复资格。显式恢复后，旧值也进入上下文。这个反例直接说明：影子命中没有证明 active 集缺少有效信息，更没有证明旧内容应该重新启用。

这里的恢复由评测脚本显式调用 `Governor.resurrect`，不能描述成正常每次问答都会自动复活旧知识。

代码依据：`governance.py:410` 的 `lfhv_report` 主要根据 archived 状态和累计 shadow hits 形成恢复候选；`governance.py:496` 的 `resurrect` 依据该候选恢复，没有在这条路径核对语义替代关系或新增任务价值。报告自身已注明 shadow 指标不能证明任务成功损失；当前恢复策略仍没有落实这一区别。

C5 的正确部分是没有把缺乏查询机会当作错误证据。能力缺口在于 `_load` 只治理 candidate/active/stale，归档正文的长期容量、保留期限或分层淘汰没有在本次治理路径中落实。仅靠 active 数量有界，不能证明完整数据库的字节规模长期有界。

附加观察（不是预注册主指标）：恢复流程调用 `mark_hits`，C1 恢复后再实际召回一次，最终 hit_count 为 2。因此该计数混合了恢复活动与真实服务活动，不能直接作为“知识实际被复用两次”的证据，更不能等同于成功改善两次任务。

## 6. 建议修复顺序与验收约束

| 优先级 | 改动目标 | 回归验收 |
| --- | --- | --- |
| 1 | 为普通知识增加本轮适用性、冗余和版本有效性判断 | B2/B5 零注入；B4 只保留新值；B1 正常召回、B3 项目隔离不退化 |
| 2 | LFHV 区分“再次命中”与“仍有效且有必要恢复”，识别替代关系与重复探测 | C2/C3 不恢复；C1 可恢复；C4 保持隔离 |
| 3 | 准入绑定原始证据，明确推断建议的类别与 scope；只对窄类型开放自动采纳 | A5 不伪装成已验证经验；A1/A2 在明确范围及冲突校验下自动化；A3/A4 继续跳过 |
| 后续独立验证 | 给长期归档设置容量/期限策略，并提供可审计的恢复与淘汰依据 | 多周期增长测试，分别看 active 数量、归档量、数据库字节和有效知识损失 |

轻量化原则：替代关系、来源与范围尽量在写入时确定；查询时先做确定性过滤，对歧义情况再评估是否需要模型仲裁。是否新增模型调用，应以消融实验和实际开销为依据，本轮没有证明某种新算法一定最好。

这 15 个案例已经被查看，后续应作为开发回归集。修复后另建未用于调参的保留集，包含正反例、同义改写、多轮更正和真实用户材料，再评价泛化。不能把修到这 15 个全部通过当作产品已充分验证。

## 7. 性能与未覆盖范围

本轮小库注入 Adapter 单次观测约 13–18 ms，仅说明这些隔离案例没有高本地开销。它不包含真实客户端启动、hook 调度、网络模型推理、完整 prompt 预填充，因此不是首 token 时间，也不是开启/关闭 MemWeave 的首 token 差值。

本轮不能回答大库 P95、长时间运行资源消耗、库规模长期受控、下游任务成功率或历史高延迟是否解决。后续需要固定模型与任务、交错执行启用/关闭的配对实验，并分别记录本地决策耗时、注入 token 数与客户端首 token 差值。

没有运行真实用户历史会话，没有新增生产数据，也没有改变正式自动采纳、过期和恢复策略。
