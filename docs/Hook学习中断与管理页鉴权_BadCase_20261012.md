# Hook 学习中断与管理页鉴权：一次真实 Bad Case 复盘

日期：2026-10-12。

**核心结论：Hook 触发、后台消费、证据准入和管理页可用是不同的验收环节。多个客户端同时没有候选，必须沿着链路查，不能只看一个“已接入”标签。**

## Case 1：Hook 还在执行，知识却停止产出

**【现象】**：Codex 和 Gemini CLI 都有新对话，却长时间没有新增候选，看起来像统一接入层把 Hook 改坏了。

**【根因】**：排查发现了几个叠加问题。

- 机器重启后 Runtime 没有恢复。Hook 仍执行召回和持久入队，但没有后台 Worker 消费，直到 Runtime 启动才处理积压。入队成功不代表学习完成。
- Gemini 的真实长会话约 33 MB。大的更新记录将用户消息挤出旧的 2 MB 尾部窗口，解析器报 `Gemini transcript contains no user prompt`。会话里有提问，当前读取窗口里却没有。
- Codex 助手在回复里写“没有实际验证资料时不能宣称支持”一类验收提醒，旧的不确定性正则却跳过整轮提炼，连本轮明确的用户规则也被一起误挡。
- Reviewer 提前删除缺少来源引用的提案，后续统计只剩零条，无法区分“模型没提案”和“模型提案被拒绝”。候选待审到期进入隔离，也会使当前待审数归零。

**【修复原则】**：

- 已初始化、同一数据库的 Hook 在 Runtime 离线时请求独立后台恢复。完成事件先持久入队，再请求恢复；当前召回保留本地路径，Hook 不等模型提炼。启动锁避免重复实例，不打开浏览器。
- 显式 `MW_RUNTIME_MODE=local`、指定 Runtime 端点或 token、数据库不匹配，均不自动切换。恢复由后续 Hook 触发，不是操作系统登录时启动服务。
- Gemini 解析与冻结统一使用最多 16 MB 的有界窗口。JSONL 保留绝对字节边界，不用旧尾部窗口的相对消息数截新窗口；重写型 JSON 继续检查消息边界与内容哈希。
- 将整轮提前否决改为逐条提案检查原文引用和工具证据。无证据的助手猜测仍拒绝，普通产出仍是待审核 candidate。
- 记录模型原始提案数、通过数、拒绝数和固定原因码；管理页及学习详情显示具体拒绝原因，不额外保存原始聊天或模型原始提案。
- 更新编译策略版本，使旧任务可在新准入策略下重试，保留历史记录。

**【验收证据】**：

- 本机受误挡的 Codex 冻结会话重试后，3 条提案通过，生成 3 条待审核候选，没有直接变成 active。
- 最新 Gemini 任务完成提炼，但 1 条提案因 `invalid_source_evidence` 被拒。这是完成消费后证据校验未通过，不能描述成“必然生成候选”。
- 在四个可定位的 Gemini 历史会话位置复核，旧窗口其中两处解析失败，新窗口四处均解析成功。这些位置按历史时间定位，不是完整保存的当时 Hook 输入，不能据此宣称全部历史失败已端到端验收。
- 本机独立后台恢复验证确认：不打开管理页，Runtime 也能重新启动。自动回归同时覆盖离线入队后恢复、后台消费、来源边界和无证据拒绝。

## Case 2：WorkBuddy 分支经过压缩节点，解析链路断开

**【现象】**：WorkBuddy 已配置 Hook，但学习任务没有候选，解析器找不到当前分支的用户提问。

**【根因】**：原解析器先过滤非消息、非工具节点，再沿父节点回溯。真实分支可能经过 reasoning 或内部压缩节点；删掉这些节点后，父子关系也被删掉了。压缩节点还可能通过 `logicalParentId` 连接原分支。

**【修复原则】**：保留这些节点的连接关系，但不读取其私有推理或内部摘要作为证据。沿当前分支回溯，支持压缩根的逻辑父节点；显式父节点断裂时拒绝解析，不借用其他分支的用户消息。循环关系也必须拒绝。

**【验收证据】**：补充跨推理节点、压缩节点、队列冻结边界、分支循环及断裂分支回归。此前本机可复核的 15 个失败会话位置均能解析，最新真实任务生成 1 条 candidate；这个结果不代表所有 WorkBuddy 会话都会产出。

## Case 3：后台恢复成功，旧管理页却报鉴权失败

**【现象】**：Runtime 健康检查通过，已打开的管理页却显示 `invalid runtime token`，列表仍是“0 条”。用户看到的零值来自加载失败，不是数据库真的为空。

**【根因】**：启动器每次重启生成新 token，页面仍持有打开时的旧 token，因此 API 返回 401。真实重启还暴露了端口竞态：终止调用返回时旧监听端口未释放，启动器立即选端口，可能转到随机端口，让旧页面留在原地址。

**【修复原则】**：

- 先通过受认证的健康响应核对旧进程，再终止并短暂等待本地端口释放。
- 同一数据库、同一本地地址的正常重启复用已有 token。数据库或地址改变时生成新凭据，错误 token 仍返回 401，不提供匿名取凭据接口。
- 初始及加载失败时数量显示“未加载”或“—”，将请求失败与真实零条分开。
- 401 提供清楚的中文入口说明。已经失效的旧链接需要通过桌面入口或 `memweave ui` 重新打开；修复不会让任意旧凭据重新获得权限。

**【验收证据】**：新增真实 Runtime 重启回归。本机验证重启前后端口、凭据一致，重启前的凭据仍可请求健康接口，错误 token 仍被拒绝。另执行管理页 JavaScript 验证 GET / POST 的 401 提示、失败后的数量占位和非鉴权错误提示。

**大白话复盘**：这次验收漏在“后台能工作”与“旧页面还能用”之间。修复学习链路后，还必须从用户打开的页面再走一遍请求，不能只看服务健康就宣布完成。

## 回归方法与口径

相关失败用例先通过，再跑定向回归。定向测试为 34 项通过，另有 5 项子测试通过：

```shell
python -m pytest tests/test_cli.py tests/test_runtime_api.py tests/test_learning_recovery.py tests/test_codex_hook_runtime.py -q
```

本机完整工作目录曾验证 714 项测试、14 项子测试通过，耗时 74.44 秒。该目录额外包含尚未发布的本地 holdout 测试；它不随本次修复提交，不能将这个总数当作 GitHub 当前检出的测试数量。

本次发布范围单独核对：**695 项测试、14 项子测试通过，耗时 71.18 秒**。本机验证时排除未发布的 `tests/test_holdout_evaluation.py`；正常检出仓库后直接运行：

```shell
python -m pytest tests -q
```

这些结果证明已覆盖的工程行为，不是开放域召回指标，也不是 Agent 任务成功率。历史真实会话仅在本机复核；公开记录不包含原始会话、凭据、内部任务标识或本机数据库。

实现入口：`runtime_recovery.py`、`hooks/shared_hook.py`、`gemini_transcript.py`、`codebuddy_transcript.py`、`learning_engine.py`、`learning.py`、`store.py`、`cli.py` 与 `knowledge_dashboard.html`。使用与诊断方法见 [Agent 接入与通用学习 API](Agent接入与通用学习API.md)。
