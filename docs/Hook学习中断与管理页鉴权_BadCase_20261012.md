# Hook 学习中断与管理页鉴权：一次真实 Bad Case 复盘

日期：2026-10-12。

**核心结论：Hook 触发、后台消费、证据准入和管理页可用是不同的验收环节。多个客户端同时没有候选，必须沿着链路查，不能只看一个“已接入”标签。**

## Case 1：Hook 还在执行，知识却停止产出

**【现象】**：Codex 和 Gemini CLI 都有新对话，却长时间没有新增候选，看起来像统一接入层把 Hook 改坏了。

**【根因】**：排查发现了几个叠加问题。

- 机器重启后 Runtime 没有恢复。Hook 仍执行召回和持久入队，但没有后台 Worker 消费，直到 Runtime 启动才处理积压。入队成功不代表学习完成。
- Gemini 的真实长会话约 33 MB。大的更新记录将用户消息挤出旧的 2 MB 尾部窗口，解析器报 `Gemini transcript contains no user prompt`。会话里有提问，当前读取窗口里却没有。
- Codex 助手在回复里写“没有实际验证资料时不能宣称支持”一类验收提醒，旧的不确定性正则却跳过整轮提炼，连本轮明确的用户规则也被一起误挡。
- Reviewer 提前删除缺少来源引用的提案，后续统计只剩零条，无法区分“模型没提案”和“模型提案被拒绝”。候选待审到期进入隔离，也会使当前待审数归零。

**【修复原则】**：

- 已初始化、同一数据库的 Hook 在 Runtime 离线时请求独立后台恢复。完成事件先持久入队，再请求恢复；当前召回保留本地路径，Hook 不等模型提炼。启动锁避免重复实例，不打开浏览器。
- 显式 `MW_RUNTIME_MODE=local`、指定 Runtime 端点或 token、数据库不匹配，均不自动切换。恢复由后续 Hook 触发，不是操作系统登录时启动服务。
- Gemini 解析与冻结统一使用最多 16 MB 的有界窗口。JSONL 保留绝对字节边界，不用旧尾部窗口的相对消息数截新窗口；重写型 JSON 继续检查消息边界与内容哈希。
- 将整轮提前否决改为逐条提案检查原文引用和工具证据。无证据的助手猜测仍拒绝，普通产出仍是待审核 candidate。
- 记录模型原始提案数、通过数、拒绝数和固定原因码；管理页及学习详情显示具体拒绝原因，不额外保存原始聊天或模型原始提案。
- 更新编译策略版本，使旧任务可在新准入策略下重试，保留历史记录。

**【验收证据】**：

- 本机受误挡的 Codex 冻结会话重试后，3 条提案通过，生成 3 条待审核候选，没有直接变成 active。
- 最新 Gemini 任务完成提炼，但 1 条提案因 `invalid_source_evidence` 被拒。这是完成消费后证据校验未通过，不能描述成“必然生成候选”。
- 在四个可定位的 Gemini 历史会话位置复核，旧窗口其中两处解析失败，新窗口四处均解析成功。这些位置按历史时间定位，不是完整保存的当时 Hook 输入，不能据此宣称全部历史失败已端到端验收。
- 本机独立后台恢复验证确认：不打开管理页，Runtime 也能重新启动。自动回归同时覆盖离线入队后恢复、后台消费、来源边界和无证据拒绝。

## Case 2：WorkBuddy 分支经过压缩节点，解析链路断开

**【现象】**：WorkBuddy 已配置 Hook，但学习任务没有候选，解析器找不到当前分支的用户提问。

**【根因】**：原解析器先过滤非消息、非工具节点，再沿父节点回溯。真实分支可能经过 reasoning 或内部压缩节点；删掉这些节点后，父子关系也被删掉了。压缩节点还可能通过 `logicalParentId` 连接原分支。

**【修复原则】**：保留这些节点的连接关系，但不读取其私有推理或内部摘要作为证据。沿当前分支回溯，支持压缩根的逻辑父节点；显式父节点断裂时拒绝解析，不借用其他分支的用户消息。循环关系也必须拒绝。

**【验收证据】**：补充跨推理节点、压缩节点、队列冻结边界、分支循环及断裂分支回归。此前本机可复核的 15 个失败会话位置均能解析，最新真实任务生成 1 条 candidate；这个结果不代表所有 WorkBuddy 会话都会产出。

## Case 3：后台恢复成功，旧管理页却报鉴权失败

**【现象】**：Runtime 健康检查通过，已打开的管理页却显示 `invalid runtime token`，列表仍是“0 条”。用户看到的零值来自加载失败，不是数据库真的为空。

**【根因】**：启动器每次重启生成新 token，页面仍持有打开时的旧 token，因此 API 返回 401。真实重启还暴露了端口竞态：终止调用返回时旧监听端口未释放，启动器立即选端口，可能转到随机端口，让旧页面留在原地址。

**【修复原则】**：

- 先通过受认证的健康响应核对旧进程，再终止并短暂等待本地端口释放。
- 同一数据库、同一本地地址的正常重启复用已有 token。数据库或地址改变时生成新凭据，错误 token 仍返回 401，不提供匿名取凭据接口。
- 初始及加载失败时数量显示“未加载”或“—”，将请求失败与真实零条分开。
- 401 提供清楚的中文入口说明。已经失效的旧链接需要通过桌面入口或 `memweave ui` 重新打开；修复不会让任意旧凭据重新获得权限。

**【验收证据】**：新增真实 Runtime 重启回归。本机验证重启前后端口、凭据一致，重启前的凭据仍可请求健康接口，错误 token 仍被拒绝。另执行管理页 JavaScript 验证 GET / POST 的 401 提示、失败后的数量占位和非鉴权错误提示。

**大白话复盘**：这次验收漏在“后台能工作”与“旧页面还能用”之间。修复学习链路后，还必须从用户打开的页面再走一遍请求，不能只看服务健康就宣布完成。

## Case 4：多个客户端看起来同时停产，实际断在不同环节（2026-10-15，诊断记录）

**【现象】**：Gemini CLI、Codex、Claude Code 都没有新增候选，用户怀疑统一 Hook 出现了共同故障。

**【核心结论】**：本次确认了 Gemini 的会话来源识别缺陷，以及 Codex、Gemini 的三条提炼失败任务。Runtime 正常、队列仍在消费，不支持“所有 Hook 都不触发”的判断。Claude 暂缺新事件证据，不能套用另外两个客户端的根因。

**【根因】**：

- **共同的提炼失败**：北京时间 10:46:41、11:01:42 的 Codex 任务，以及 11:31:46 的 Gemini 任务，最终均报 `review model returned no message content`。该错误表示响应中无法取得预期的 `choices[0].message.content`，不等同于已经确定欠费、代理异常或客户端故障。三条任务都已尝试 3 次并进入 `failed`；现有队列只消费 `queued`，服务恢复不会自动重放这些终态任务。历史没有保存响应结构诊断，无法继续还原上游当时返回了什么。
- **Gemini 把工具返回当成新提问**：真实 transcript 会将 `functionResponse` 记录为 `type=user`。解析器只按 `type=user` 加非空正文选最后一条消息，而 `_content()` 又会展开工具响应正文，结果将工具输出选为 USER REQUEST，从这里重新切轮，丢掉前面的真实用户请求和工具调用。这是解析层的来源混淆，不是模型没有执行 Hook。
- **Gemini 把注入记忆当成用户证据**：客户端的 `content` 包含扩展后的消息和 `<hook_context>`，`displayContent` 保留用户可见的原始输入。当前解析器不区分这两种来源，把召回记忆也送入 USER REQUEST。除了干扰提炼，还存在旧记忆被重新引用成“用户新声明”的证据回流风险；本次未发现因此新增的错误候选。
- **不能把全部零提案归为解析故障**：部分 Gemini 任务停在取消提示，边界内没有后续助手回答；Codex 下午完成的任务返回零提案，也不能据此判断 Hook 失败或强制补一条知识。提问、临时输出及缺少可复用证据的回合允许零产出。
- **Claude 的断点尚未证实**：本机默认会话目录最新修改停在 10 月 13 日，排查时没有发现正在运行的 Claude 进程，今天数据库也没有 Claude 学习任务。默认配置仍有 Hook，部分自定义配置文件没有显式声明 Hook；仅凭自定义文件缺少声明，不能判断客户端合并后的配置一定没有 Hook，也不能证明用户实际使用了该启动方式。需要取得实际客户端的新事件、有效配置及会话路径后才能定因。

**【修复原则，尚未实施】**：

- 解析器区分真实用户文本、工具返回和系统附加上下文；不能仅用 transport 的 `user` 角色判断人的发言。保留原始轮次身份和冻结边界，工具返回应关联原调用，不冒充用户声明；不得靠跨轮借证据补齐缺失。
- Gemini 的扩展输入与用户可见输入分开处理，Hook 上下文不得作为新的用户证据。不能只靠删除任意同名字符串，也不能丢弃同轮的真实工具事件。
- 改解析器后，旧冻结任务的内容哈希可能变化；历史重放必须显式处理版本和来源一致性，不能关闭哈希检查或直接篡改生产任务状态。
- 提炼响应异常记录脱敏后的结构原因，区分缺正文、无效协议、合法空提案和证据拒绝。即使 HTTP 200，缺少 `proposals` 的对象也不能默认为正常零提案。
- 失败任务保留原因和次数，提供有界、可审计的恢复路径；不无限重试，不让前台 Hook 等模型，也不为增加候选数量放宽证据准入。

**【排查与复现证据，非修复验收】**：

- 截至北京时间 2026-10-15 16:10，受认证 Runtime 健康检查正常，版本为 `0.5.0a2`；今天 Codex 有 1 条完成、2 条失败，Gemini 有 10 条完成、1 条失败。完成任务均为 `reviewer_returned_zero`，没有新增提案；当前服务可用不能反证上午没有失败。
- 对当天 10 条已完成 Gemini 队列任务按各自冻结边界只读复核：7 条的末尾用户消息混有召回上下文，2 条将工具响应选成用户消息，4 条没有后续 Gemini 消息，其中 3 条末尾有取消提示。这些统计维度有重叠，不能相加，也不能当作任务收益指标。
- 一个真实冻结位置的工具响应前明明有 1 次工具调用，解析后却是 0 个工具事件。使用完全合成的“用户规则 → 工具调用 → user 角色工具返回 → 助手确认”结构独立复现，结果同样把工具输出当成用户请求，并丢失原工具事件；另一个合成结构复现了 `<hook_context>` 混入用户证据。
- 当前提炼接口的纯合成规则探针收到 HTTP 200、正常正文和 1 条提案；没有将私人对话用于该探针，也没有向生产知识库写入诊断候选。它只证明当时接口能够响应，不代表真实客户端已恢复产出。
- 本次仅诊断并记录，未修改解析器、客户端配置、生产数据库或重试失败任务；不能将此记录称为“修复完成”或套用下文 10 月 12 日的历史回归成绩。

**大白话复盘**：角色叫 user，不代表内容就是人说的话。客户端为了把工具结果送回模型，也可能使用 user 角色；接入层必须识别消息的来源和用途，否则后台看起来处理成功，实际送给提炼器的已经不是那一轮任务。

## Case 5：Claude 自定义配置残留旧命令，Git Bash 吞掉脚本路径（2026-10-15）

**【现象】**：继续排查 Claude，发现默认 `settings.json` 的 Hook 命令可以执行，但自定义 `settings-gemini38.json` 的 UserPromptSubmit 和 Stop 仍是旧命令。将现有命令交给本机 Git Bash 执行，Python 以退出码 2 报找不到 Hook 脚本，事件尚未进入统一执行器。

**【根因】**：

- Git 历史定位到 `1483007`（统一接入层）：原安装逻辑始终给脚本路径加引号，统一安装器改为 `subprocess.list2cmdline()`。这是 Windows 参数引用规则，脚本路径不含空格时不会加引号；Git Bash 随后将路径反斜杠当作转义符，路径变形。框架将 Hook 从含空格的项目路径搬到无空格的用户目录后，暴露了这个条件。
- 10 月 8 日 `9c1e0ef` 已为 Codex 等增加编码命令，但已提交的 Claude profile 未启用。排查开始时工作区已有 `windows_encoded_command=True` 的修正，默认配置也已经修正；自定义 Gemini 模型配置却残留 10 月 8 日写入的旧 Hook。只检查默认配置，不能证明所有实际启动入口都已经迁移。
- 这是可以复现的 Claude 接入缺陷，但本机没有今天的 Claude 新会话、实际运行进程和有效配置快照，仍不能证明用户今天一定走了该自定义入口，也不能将所有零产出都归因于它。

**【修复原则】**：Claude 在 Windows 使用显式 PowerShell 编码命令，两个命令字段保持一致，不能依赖客户端一定识别 `commandWindows`。只替换属于 MemWeave 的 Hook，保留模型配置、环境设置和第三方 Hook；有备份地修复已定位的自定义配置，不批量给无关配置增加 Hook。

**【验收证据】**：

- 同一台机器、同一脚本、相同无副作用输入：统一前的显式引号命令成功，统一后的 `list2cmdline()` 命令退出码 2，当前编码命令成功。由此确认命令生成的回归点，不需要猜测模型或网络原因。
- 新增 Git Bash 实际执行回归，覆盖无空格路径，以及中文、空格和单引号路径。将 Claude profile 临时替换为旧生成方式运行，前一种路径失败；使用当前实现两种路径均通过。测试还验证召回、Stop 持久入队、后台消费后生成 candidate，以及不破坏第三方 Hook 和重复安装幂等性。候选验收使用隔离数据库和固定 Reviewer，不代表线上模型效果。
- 本机修复 `settings-gemini38.json` 前保存独立备份；修复后模型和环境等非 Hook 设置保持一致。默认配置无需变更。两份配置的 UserPromptSubmit、Stop 命令均通过 Git Bash 无副作用探针，返回合法 JSON、退出码 0、无 stderr。没有将诊断任务写入生产知识库。
- 定向回归 124 项、4 项子测试通过；当前完整工作目录全量回归 746 项、14 项子测试通过，耗时 73.83 秒。该总数包含本地尚未发布的评测测试，不替换发布版历史口径。真实客户端重新加载配置后的新对话产出仍需单独验收；本节不宣称已解决 Case 4 的 Gemini 解析和提炼服务历史失败问题。

**大白话复盘**：不是模型突然不肯总结，而是旧启动入口还留着一条会把文件路径拆坏的命令。配置写得像 Windows 命令，不代表经过 Git Bash 还能原样执行。回归必须从实际 Shell 执行到候选入库，不能只比较配置字符串。
